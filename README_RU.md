# airflow-provider-yandex-admetrica

Провайдер Apache Airflow для [API отчётов Яндекс Метрики для медийной рекламы (AdMetrica)](https://yandex.ru/dev/admetrica/doc/ru/) — выгрузка статистики медийных рекламных кампаний.

## Установка

```bash
pip install airflow-provider-yandex-admetrica
```

Требуется Python 3.10+ и Airflow 2: `apache-airflow>=2.9.1,<3.0`.

**Нужен тариф Метрика Про.** API отчётов входит в него, и аккаунту без тарифа доступ к `/v1/stat/data` закрыт при любом валидном токене. Приложение создаётся на [oauth.yandex.ru](https://oauth.yandex.ru/client/new) с доступами `mediametrika:read` и `mediametrika:write` — инструкция Яндекса требует обоих, хотя провайдер только читает.

## Настройка подключения

**Один коннекшн — один рекламодатель.** Токен и рекламодатель, за которого он работает, живут вместе, поэтому рекламодатель назван в одном месте, и всё остальное — записи, ключи S3, имена таблиц — читает его оттуда.

Создайте в Airflow подключение типа **HTTP** с `conn_id = yandex_admetrica_default` (или любым другим именем, которое вы передадите оператору):

| Поле в интерфейсе Airflow | Значение |
|---|---|
| **Password** | OAuth-токен **без** префикса `OAuth `. Провайдер сам пишет схему, когда собирает `Authorization: OAuth {token}`. Пароль, сохранённый вместе с префиксом, тоже принимается — префикс снимается, чтобы исходящий заголовок не удвоил его |
| **Extra** | `{"advertiser_id": 17004}` |

`advertiser_id` можно записать числом или строкой: `extra` — это JSON, который набирают руками, и `17004` и `"17004"` называют одного рекламодателя. Значение обязано быть целым числом больше нуля — флаг, дробь или ноль не называют рекламодателя, и таска падает с сообщением об этом.

Больше ни одно поле коннекшена не читается. **Host** игнорируется: адрес API фиксирован — `https://api.media.metrika.yandex.net`.

`AdmetricaHook.test_connection()` отвечает, работает ли коннекшн: запрашивает список кампаний рекламодателя — этот запрос разом проверяет всё, от чего зависит выгрузка (токен принят, рекламодатель существует, аккаунту доступен API), — и возвращает `(True, "Connected to AdMetrica as advertiser 17004: 42 campaigns are readable.")` либо `(False, <текст отказа с замаскированным токеном>)`. Это метод для вызова из DAG или из консоли, а не кнопка **Test** в UI: собственного типа коннекшена провайдер не регистрирует, поэтому коннекшн типа HTTP проверяет хук HTTP-провайдера.

Диагностика использует второй коннекшн, он описан в разделе [Подключение к Loki](#подключение-к-loki).

## Быстрый старт

```python
from airflow.decorators import dag
from airflow.models.param import Param
from airflow_provider_yandex_admetrica.operators.stats import YandexAdmetricaStatsOperator


@dag(
    schedule=None,
    start_date=None,
    catchup=False,
    params={"date": Param("2026-08-20", type="string")},
)
def admetrica_one_day():
    YandexAdmetricaStatsOperator(
        task_id="collect",
        admetrica_conn_id="yandex_admetrica_default",
        date="{{ params.date }}",
        dimensions=["am:e:placement", "am:e:deviceType"],
        metrics=["am:e:renders", "am:e:clicks", "am:e:ctr"],
        base_dir="/tmp/yandex_admetrica",
    )


admetrica_one_day()
```

**Единица оператора — один день.** Оператор получает одну дату и собирает за неё статистику по всем кампаниям рекламодателя. Период разворачивает DAG, отдавая каждый день отдельным map index: падение одного дня не трогает остальные, а повтор дня — это clear его map index. Пример DAG кладёт в map index не только сбор, а весь путь дня — обе выгрузки и загрузку в BigQuery, — так что и грузится каждый день сам по себе; см. [Примеры](#примеры).

Оператор пишет файлы JSONL и возвращает `list[dict]` — по записи на каждый записанный файл:

```python
[
    {"kind": "stats", "date": "2026-08-20", "path": "/tmp/…/stats/2026-08-20.json", "advertiser_id": 17004},
    {"kind": "dict",  "date": "2026-08-21", "path": "/tmp/…/dict/campaigns/2026-08-21.json", "advertiser_id": 17004},
]
```

`advertiser_id` едет в каждой записи, потому что задачи ниже по потоку строят из него ключ S3 и имя таблицы, а взять его больше неоткуда: рекламодатель назван в коннекшене, который открывает только хук.

**Рассчитывайте на долгую таску.** День — это по запросу на кампанию, плюс ещё страница на каждую полную страницу кампании, плюс обход списка кампаний. Рекламодатель с 70 кампаниями стоит около 70 запросов на день обычного объёма, каждый отделён паузой `request_delay` и ограничен таймаутом 30 с. Шторм ретраев добавляет любому из них до 7 с задержек, когда паузу выбирает лестница, — но сервер, приславший `Retry-After`, называет паузу сам, и каждая из трёх ступеней стоит тогда до 300 с, то есть один запрос способен держать таску 15 минут. У 400, который API формулирует как `query_error`, лестница своя: 65 с пауз плюс ещё три запроса, каждый ограничен тем же таймаутом 30 с и эмпирически стоит около 10 с там, где упирается в дедлайн, — такой запрос держит таску около 155 с. Подбирайте `execution_timeout` под число дней в прогоне — пример DAG отводит два часа.

### Параметры оператора

| Параметр | По умолчанию | Значение |
|---|---|---|
| `admetrica_conn_id` | `"yandex_admetrica_default"` | Коннекшн, называющий рекламодателя и хранящий токен |
| `date` | — | Выгружаемый день, `YYYY-MM-DD`. Обязателен |
| `dimensions` | — | Группировки, например `["am:e:placement", "am:e:deviceType"]`. Обязателен; может быть пустым, и тогда отчёт — одна строка на кампанию. Не больше 10 |
| `metrics` | — | Метрики, например `["am:e:renders", "am:e:clicks"]`. Обязателен. Не больше 20 |
| `filters` | `None` | Выражение фильтра, уходит в API как `filters`. Не задан — в запросе отсутствует |
| `accuracy` | `"full"` | Точность семплирования. `"full"` запрашивает полную выборку, и именно это удерживает цифры от плавания между прогонами; другое значение меняет точность на скорость |
| `include_undefined` | `True` | Сохраняет строки, у которых первая группировка не определена. Без этого API их выбрасывает, и сумма перестаёт сходиться с `totals`. При `None` параметр в запрос не кладётся вовсе, и решает то, что API берёт по умолчанию |
| `limit` | `10000` | Строк на страницу статистики. API допускает до 100 000 |
| `request_delay` | `0.2` | Секунд тишины между двумя запросами. AdMetrica не публикует ни квот, ни частоты, поэтому темп задан консервативно — поднимите или опустите его, измерив живого рекламодателя |
| `timezone` | `None` | Уходит в API как `timezone`. Не задан — в запросе отсутствует |
| `lang` | `None` | Уходит в API как `lang`; определяет язык, на котором API пишет `name` группировки. Не задан — в запросе отсутствует |
| `extra_params` | `None` | Дополнительные параметры запроса и место для значения параметризованного имени: `{"goal_id": 12345}`, `{"currency": "RUB"}`. Только добавляет имена, которых в запросе ещё нет, и ничего не переопределяет — см. [Зарезервированные параметры](#зарезервированные-параметры) |
| `base_dir` | `"/tmp/yandex_admetrica"` | Корень локальной раскладки |
| `collect_dictionaries` | `True` | Выгружать ли заодно словарь кампаний |
| `loki_conn_id` | `None` | Коннекшн для [диагностики запросов](#диагностика-запросов-в-loki-loki_conn_id). Без него клиент не конструируется и ничего не отправляется |

`date`, `admetrica_conn_id`, `loki_conn_id` и `base_dir` — шаблонные поля.

Запрос проверяется до отправки, так что неверно настроенный отчёт не стоит ничего. `ValueError` отвечает на пустой `metrics`, больше 20 метрик, больше 10 группировок и `limit` вне диапазона 1…100 000, называя, что именно не так. `date` проверяется на формат `YYYY-MM-DD` самим хуком, поэтому DAG, вызывающий `get_stats` напрямую, получает тот же отказ: это и день, который спрашивают у API, и день, проставленный в каждую запись, и имя файла, а приходит он отрендеренным из шаблона.

#### Зарезервированные параметры

`extra_params` не принимает `ids`, `date1`, `date2`, `metrics`, `dimensions`, `preset`, `limit`, `offset`, `sort`, `accuracy`, `include_undefined`, `filters`, `timezone` и `lang`; любой из них даёт `ValueError` до того, как что-либо будет запрошено. Каждый из них — либо сам задаваемый вопрос, либо ответ на то, как он задан, и молчаливое переопределение было бы невидимо в данных: другой `date1` запросил бы другой день, а записи всё равно несли бы дату оператора; `accuracy` и `include_undefined` сняли бы ровно те дефолты, что стоят против плавающих и урезанных цифр, — причём сверка полноты прошла бы, потому что `total_rows` согласован с урезанной выборкой. `preset` позволяет API самому задать метрики и группировки отчёта, тогда как значения раскладываются по запрошенным именам по позиции, и цифры легли бы под чужими ключами. У `filters`, `timezone`, `lang`, `accuracy` и `include_undefined` есть собственные параметры оператора, так что маршрут через `extra_params` им не нужен.

### Как собирается день

- **По запросу на кампанию.** Группировки по кампании в API нет, а кампании, перечисленные в `ids`, суммируются, поэтому отдельный запрос на кампанию — единственный способ сохранить разрез. Список кампаний берётся один раз на экземпляр таски — хук живёт на один `execute`, поэтому прогон, разложенный по map index на день, обходит список раз в день — и обслуживает и статистику, и словарь этого дня. Кампания, для которой ответ не назвал пригодного `campaign_id`, роняет выгрузку: `ids` обязателен и называет одну кампанию, поэтому строки такой кампании не может запросить ничто, а день, записанный без них, оказался бы коротким и не сказал бы об этом.
- **Все статусы кампаний.** Параметр `status` в запрос не уходит: архивная кампания крутилась в прошлом, и её статистика так же реальна, как у активной, а фильтр здесь молча укорачивал бы каждую перезаливку прошлого периода. По `date_start`/`date_end` кампании тоже не фильтруются — это заявленные даты кампании, а не обещание того, где лежат показы.
- **`date1 = date2 = <день>`.** У отчёта нет собственной даты, поэтому день запрашивается по одному, и провайдер сам проставляет его в каждую запись. Однодневная выборка вдобавок достаточно мала, чтобы семплирование было маловероятно.
- **`sort` называет все запрошенные группировки.** Отчёт по ним агрегирован, поэтому комбинация их значений задаёт полный и воспроизводимый от страницы к странице порядок; сортировка по метрике его не даёт — у длинного хвоста площадок `renders=1`.
- **Пагинация проверяется, а не принимается на веру.** Строка опознаётся по тому, что совпало у её группировок, и строка, встреченная дважды в пределах одной кампании, роняет день: перекрывающиеся страницы — это страницы, которые заодно что-то пропускают, а по количеству строк одно от другого не отличить. Та же комбинация в двух разных кампаниях — штатная ситуация, одна площадка крутится в нескольких, поэтому множество увиденных строк обнуляется на каждой кампании.
- **Обход останавливается по короткой странице, а не по итогу.** День кампании читается, пока не придёт страница короче запрошенной, — это собственные слова отчёта о том, что строки кончились. Объявленный итог — число об отчёте, а не сам отчёт, и заниженный на страницу итог оставил бы день без хвоста: 10 437 строк, объявленных как 10 000, при `limit=10000` дают ровно полную первую страницу и сходятся с итогом. Цена — один лишний запрос, когда день кампании кончается ровно на границе страницы. Список кампаний обходится по тому же правилу.
- **Полнота сверяется с `total_rows`.** Расхождение с точным значением роняет день `AirflowException`: потерянные между страницами строки теряются молча, и то, чего в файле нет, обнаруживается неделями позже. Если ответ взвёл `total_rows_rounded`, то же расхождение — только предупреждение: число само объявлено приближением, и записаны собранные строки.
- **Нечитаемый признак полноты роняет день.** Каждая страница обязана нести целочисленный `total_rows`, булев `total_rows_rounded`, если поле вообще есть (`null` в нём читать нечем, а страница без такого поля объявляет точный итог), и — пока итоги точные — тот же итог, что и страницы до неё. Без итога дню не с чем сверяться, `"false"`, прочитанное как истина, сняло бы точную сверку целиком, а два разных точных итога дают два ответа на вопрос, какой длины отчёт. Выгрузка, которая не может прочитать свой признак полноты, не может и заявлять полноту, поэтому падает. Со своим `total` список кампаний живёт по тому же правилу.
- **Оговорки попадают в лог таски.** `sampled` — WARNING с `sample_share`, `sample_size` и `sample_space`; `contains_sensitive_data` — WARNING о том, что день короче на скрытые API строки; `data_lag` — INFO.

## Формат записей

### Статистика

Служебные поля плоские и типизированные, переменная часть — два вложенных объекта:

```json
{"date": "2026-08-20", "advertiser_id": 17004, "campaign_id": 123456,
 "dimensions": {"placement": {"name": "Главная страница", "id": 55},
                "device_type": {"name": "mobile"}},
 "metrics": {"renders": 12345, "clicks": 67, "ctr": 0.54}}
```

Вложенность превращает новое поле в ответе в изменение JSON-значения, а не схемы таблицы, и позволяет двум строкам одного дня нести разные поля, не выравнивая одну по другой. API описывает значение группировки как объект с произвольными строковыми ключами, из которых гарантирован только `name`, — набор полей внутри выбирает ответ.

| Ключ | Откуда берётся |
|---|---|
| `date` | Проставляет провайдер: даты в отчёте нет, поэтому день, за который сделан запрос, и есть день строки |
| `advertiser_id` | Из `extra` коннекшена |
| `campaign_id` | Кампания, на которую был направлен запрос |
| `dimensions` | По ключу на каждую запрошенную группировку, в порядке запроса. Значение — объект, каким его вернул API, **ровно** с теми полями, с которыми он пришёл: ничего не отбрасывается, ничего не добавляется, имена полей внутри не трогаются |
| `metrics` | По ключу на каждую запрошенную метрику, в порядке запроса, со значением из ответа |

**По ключу на запрошенное имя — и два имени могут хотеть один ключ.** Оба способа записи параметризованного имени нормализуются в один ключ, поэтому запрос сразу `am:e:goal12345Reaches` и `am:e:goal<goal_id>Reaches` с `extra_params={"goal_id": 12345}` пишет `goal12345_reaches` один раз: в записи остаётся последнее значение, WARNING называет оба имени их позицией в запросе, и одной из двух запрошенных метрик в файле не будет. Задавайте одно написание, но не оба. Сами имена в лог не попадают: имя — это текст вызывающей стороны, и в нём может оказаться что угодно, включая учётные данные.

**Именование ключей.** Общий префикс `am:e:` снимается, параметр, вписанный в имя, заменяется своим значением, а оставшийся camelCase переводится в snake_case. Одно правило обслуживает и группировки, и метрики, потому что API называет их одинаково:

| Запрошенное имя | Ключ записи |
|---|---|
| `am:e:placement` | `placement` |
| `am:e:deviceType` | `device_type` |
| `am:e:operatingSystemRoot` | `operating_system_root` |
| `am:e:interest2d1` | `interest2d1` |
| `am:e:renders` | `renders` |
| `am:e:videoCompletePercent` | `video_complete_percent` |
| `am:e:goal12345Reaches` | `goal12345_reaches` |
| `am:e:goal<goal_id>Reaches` при `extra_params={"goal_id": 12345}` | `goal12345_reaches` |

Параметризованное имя доходит до API в двух написаниях — значение вписано в само имя либо в имени стоит подстановка, а значение едет отдельным полем, — и подстановка значения делает ключ записи одинаковым для обоих, так что отчёт, переписанный с одного написания на другое, продолжает писать ту же колонку. Подстановка, на которую не нашлось параметра, остаётся в ключе под собственным именем и логируется WARNING, называющим имя его длиной: если бы подстановку просто выбрасывали, все цели аккаунта слились бы в одну колонку, и слияние было бы заметно только как завышенные цифры.

Этот ключ — публичный контракт: именно его аналитик пишет в `JSON_VALUE(dimensions, '$.device_type')`.

Порядок ключей фиксирован — служебные, затем группировки в порядке запроса, затем метрики в своём, — поэтому файлы, записанные одним и тем же запросом, побайтово сравнимы, а перезаливка читается как diff.

Строка, в которой значений не столько, сколько было запрошено, роняет день. Ответ имён не называет, и позиция — единственное, что связывает число с метрикой, поэтому строку другой длины не прочитать: часть ключей осталась бы пустыми либо часть чисел была бы выброшена, а в `total_rows` такая строка входит наравне с целой, так что сверка полноты прошла бы и файл выглядел бы целым. Пустое значение записывается таким, каким пришло. Метрика, которая делит или считает цену, — `am:e:ctr`, `am:e:cpm`, `am:e:cpc`, `am:e:cpa<goal_id>`, семейство `video*Percent`, семейство `am:e:ecommerce<currency>Revenue` — пуста везде, где нет её знаменателя или её стоимости, поэтому отчёт, запросивший только такие метрики, отвечает строками из пустых чисел; пустое значение **группировки** — ровно то, что просит `include_undefined=True`. И то и другое доезжает до файла как JSON `null`, который BigQuery читает как NULL.

### Словарь кампаний

В статистике есть только `campaign_id`; название кампании живёт в отдельном словаре, потому что приходит из другого эндпоинта. Словарь плоский, его поля названы ровно так, как их называет management API:

```json
{"snapshot_date": "2026-08-21", "campaign_id": 123456, "name": "Летняя кампания",
 "status": "active", "date_start": "2026-06-01", "date_end": "2026-08-31",
 "advertiser_id": 17004, "advertiser_name": "ООО Ромашка"}
```

`snapshot_date` — это день, **когда выполнялась выгрузка**, а не день, о котором она рассказывает: management API отдаёт текущее состояние кампаний, и спросить его о прошедшем дне невозможно. Проставляет поле оператор, он же именует этой датой файл и возвращает её в `date` результата, поэтому колонка строки, ключ, по которому она грузится, и партиция, в которую она попадает, всегда называют один день. Дата берётся из `start_date` прогона, а не из часов машины, поэтому прогон, у которого дни разложены по map index, даёт один снапшот даже когда пересекает полночь.

Словарь выгружается на каждый день прогона, поэтому один и тот же файл появляется в результате каждого map index. Грузить его столько раз, сколько в периоде дней, незачем: возьмите запись `kind="dict"` любого дня, который до неё дошёл, и загрузите снапшот один раз за прогон — так делает пример DAG.

Путь у всех map index тоже один, потому что одна и дата снапшота, так что одновременно работающие map index пишут в один файл. Запись атомарна — строки уходят во временный файл, который одним шагом перемещается на путь, — поэтому загрузка всегда находит целый снапшот, а не обрезанную середину двух. Последовательная mapped-таска (`max_active_tis_per_dag=1`, как в примере DAG) или `collect_dictionaries=True` только на одном индексе снимают и лишнюю работу.

Измерения, которые ответ несёт рядом с этими полями — расход, показы, дней осталось, конверсии, — описывают кампанию на момент запроса, а не саму кампанию, а измерению место в таблице статистики. Они не записываются.

### Схема таблиц BigQuery

Обе таблицы описываются явно. `autodetect` определял бы вложенные поля по началу файла и терял бы те, что встречаются дальше.

Статистика, партиционирование по `date`:

| Колонка | Тип |
|---|---|
| `date` | DATE |
| `advertiser_id` | INTEGER |
| `campaign_id` | INTEGER |
| `dimensions` | JSON |
| `metrics` | JSON |

Словарь кампаний, партиционирование по `snapshot_date`: `snapshot_date` (DATE), `campaign_id` (INTEGER), `name`, `status`, `date_start`, `date_end` (STRING), `advertiser_id` (INTEGER), `advertiser_name` (STRING).

Адресация партиции декоратором `table$YYYYMMDD` позволяет `WRITE_TRUNCATE` перетереть один день и не тронуть остальную таблицу.

## Раскладка файлов

Локально `run_id` изолирует друг от друга два прогона, выгружающих один и тот же день:

```
{base_dir}/{dag_segment}/{run_segment}/{advertiser_id}/stats/{date}.json
{base_dir}/{dag_segment}/{run_segment}/{advertiser_id}/dict/campaigns/{snapshot_date}.json
```

`dag_segment` и `run_segment` называют DAG и прогон: идентификатор, в котором каждый символ вне `[\w-]` — букв, цифр, подчёркивания и дефиса — заменён подчёркиванием, поэтому `run_id` с временной меткой, двоеточиями и плюсом всё равно годится в имя каталога на любой файловой системе, а следом через дефис — первые восемь символов его SHA-1. Дайджест — это то, чем два идентификатора остаются различимы после замены, сделавшей их неотличимыми: так выглядят `manual:a` и `manual/a`. Читаемая часть обрезается до того, что оставляют от 255 байт дайджест и дефис, поэтому сегмент годится в имя каталога на любой файловой системе: Airflow принимает `dag_id` и `run_id` длиной до 250 символов, а символ вне ASCII занимает больше одного байта. Обрезка ничего не стоит: дайджест берётся от целого идентификатора.

DAG нужен наравне с прогоном потому, что Airflow держит `run_id` уникальным в пределах своего DAG и не шире. Один коннекшен называет одного рекламодателя, поэтому нескольких рекламодателей обслуживают несколько DAG'ов, и двум из них на одном расписании достаётся один и тот же `scheduled__<logical_date>`: на общем `base_dir` каталог, названный одним прогоном, оказался бы одним каталогом, в который они собирают оба, а `cleanup` в примере DAG сносит его целиком.

День санитизируется одной заменой, так что ничто отрендеренное в `date` не адресует файл вне `base_dir`.

В S3 `run_id` отсутствует, день перетирается — история не хранится:

```
{S3_PREFIX}/{advertiser_id}/stats/_year=2026/_month=08/_day=20/_date=20260820/2026-08-20.json
{S3_PREFIX}/{advertiser_id}/dict/campaigns/_year=2026/_month=08/_day=21/_date=20260821/2026-08-21.json
```

Файлы — JSONL: по одному JSON-объекту на строку, UTF-8, с `ensure_ascii=False`, чтобы названия площадок и кампаний читались в самом файле. JSONL — единственный формат: набор колонок не выводится из запроса и может различаться у двух строк одного дня.

### День без данных

День, на который API не вернул ни строки, **не создаёт файла** и ничего не добавляет в результат оператора. Таска остаётся зелёной — кампания без показов в конкретный день это обычное состояние большинства кампаний рекламодателя.

Следствие стоит проговорить: **файл, уже лежащий в S3 за этот день, остаётся ровно таким, каким был.** Перезаливка дня, который с тех пор опустел, его не очистит. Удаление такого дня — ручная операция над бакетом и над партицией BigQuery.

То же и со словарём: рекламодатель, у которого список кампаний вернулся пустым, файла словаря не создаёт. В остальном словарь выгружается и в день без статистики — список кампаний от показов не зависит.

### Смена набора группировок и метрик

Эти два параметра задают форму записи, поэтому их смена меняет файлы, записанные **начиная с неё**. Ранее выгруженные файлы остаются как есть, под теми ключами, с которыми были записаны.

Автоматически эти формы ничто не примиряет, и примирять не нужно: `dimensions` и `metrics` — колонки JSON, поэтому запись с новым ключом грузится в существующую таблицу без правки схемы. Запрос, называющий ключ, которого в старых файлах нет, вернёт по ним NULL, а не ошибку.

Приведение истории к новой форме — ручная операция: перезалейте нужный период либо удалите его и выгрузите заново.

## Отказы, ретраи и лог таски

| Ситуация | Поведение |
|---|---|
| 429 и любой 5xx | Повтор с backoff 1 / 2 / 4 с, всего 4 попытки на запрос. Заголовок `Retry-After` старше лестницы в обоих написаниях — секунды и HTTP-дата — с потолком 300 с; более долгое ожидание держало бы слот таски всё это время, а уронить день дешевле |
| Запрос, который не унесла сеть | Повтор по той же лестнице |
| 401 или 403 | Падает сразу. Токен долгоживущий, механизма обновления здесь нет, поэтому следующая попытка получила бы тот же отказ. Любой из двух статусов говорит одно и то же о токене, который API не принимает |
| 400, чьё тело называет `error_type: query_error` | Повтор по собственной лестнице 5 / 15 / 45 с, всего 4 попытки на запрос. Запрос исправен, а неудачным оказался момент, и размах лестницы минутный, потому что стоящее за таким отказом условие дрейфует на этом масштабе |
| 400 с любым другим `error_type` и прочие 4xx | Падает сразу, с текстом сервера, вынутым из тела. Отказ получает сам запрос, и повтор принесёт тот же ответ |
| HTTP 200, из которого не читаются строки | Падает, называя, что было в теле вместо них. **Ноль никогда не бывает зелёным, если пришёл из отказа** — дальше передаётся только корректный ответ, в том числе пустой |
| Строка несёт не столько значений группировок или метрик, сколько было запрошено | `AirflowException` с кампанией, днём и обоими числами: позиция — единственное, что связывает значение с именем, а в `total_rows` такая строка входит наравне с целой |
| Собранные строки расходятся с точным `total_rows` | `AirflowException` |
| То же расхождение при взведённом `total_rows_rounded` | WARNING; записаны собранные строки |
| Страница без целочисленного `total_rows` или с присутствующим небулевым `total_rows_rounded` | `AirflowException`: нечитаемый признак полноты не оставляет дню, с чем сверяться, и короткий день прошёл бы незамеченным |
| Две страницы одного дня кампании объявляют разные точные итоги | `AirflowException`: число, с которым сверяются строки, сменилось под обходом |
| Собранные кампании расходятся с объявленным `total` | `AirflowException`: пропавшая из списка кампания уносит с собой всю свою статистику |
| Страница списка кампаний без целочисленного `total` либо две страницы с разными итогами | `AirflowException` — по той же причине, по какой те же ответы роняют день кампании |
| Кампания, у которой `campaign_id` — не положительное целое | `AirflowException` с названием этой кампании. Статистика запрашивается по одной кампании за раз и называется этим id, поэтому такую кампанию не может запросить ни один запрос — а день, записанный без её строк, выглядел бы полным |
| Список кампаний, повторивший `campaign_id` | `AirflowException` с названием этой кампании. Список, повторяющий кампанию, — это список, по которому не движется `offset`, поэтому страницы после неё принадлежат обходу, переставшему продвигаться |
| Обход, которому эндпоинт всё время отвечает полными страницами | `AirflowException` по исчерпании бюджета страниц. Бюджет — десять миллионов строк на кампанию за день и миллион кампаний в списке рекламодателя, делённые на строки, которые запрашивает страница этого обхода: обход статистики запрашивает `limit`, поэтому при `limit=10000` ему разрешена 1000 страниц, а при `limit=100` — 100 000; список кампаний запрашивает фиксированную 1000, и ему разрешена 1000 страниц. Страница настолько маленькая, что до потолка по строкам нужно больше 100 000 запросов, упирается в запросы |
| `sampled` | WARNING с `sample_share`, `sample_size` и `sample_space` |
| `contains_sensitive_data` | WARNING: часть строк скрыта API |
| `data_lag` | INFO |

Одному запросу отведено 30 с, после чего он считается запросом, который не унесла сеть.

**Каждая неудачная попытка оставляет в логе таски одну строку**, включая последнюю, чтобы минута ожидания читалась как хроника, а не как тишина. Страница, вернувшаяся не с первой попытки, добавляет одну INFO-строку с номером этой попытки — `recovered on attempt 3/4`, — так что серия предупреждений несёт собственный конец; страница, пришедшая с первой попытки, не говорит ничего, и здоровая выгрузка оставляет лог таким, каким он был. Исключение одно — попытка, на которой остановили саму таску: `BaseException`, не являющийся `Exception` (истёкший `execution_timeout`, SIGTERM), не пишет строки и не отправляет события намеренно, потому что причина уже лежит в логе таски Airflow, а push задержал бы остановку на своё время.

```
AdMetrica stat campaign_id=123456 date=2026-08-20 offset=1: attempt 1/4 failed — HTTP 429. Retrying in 1 s
AdMetrica stat campaign_id=123456 date=2026-08-20 offset=1: attempt 2/4 failed — HTTP 502. Retrying in 2 s
AdMetrica stat campaign_id=123456 date=2026-08-20 offset=1: attempt 3/4 failed — no response, ConnectionError. Retrying in 4 s
AdMetrica stat campaign_id=123456 date=2026-08-20 offset=1: attempt 4/4 failed — HTTP 500, code 42: internal error
AdMetrica campaigns offset=0: failed, not retryable — HTTP 200, no readable rows (payload_kind=rows_absent)
```

`Retrying in N s` появляется только там, где пауза действительно будет, — по этому слову последняя попытка и читается как последняя. Отказ, к которому лестница неприменима, читается как `failed, not retryable` вместо дроби, потому что дробь пообещала бы попытки, которых запросу не дадут. В строке только разобранные поля: HTTP-статус, названный телом отказ, метка того, что стояло вместо строк, позиция, на которой сломался JSON, тип сетевого сбоя, — поэтому одна попытка остаётся одной строкой, что бы сервер ни написал. Сырой ответ принадлежит другому каналу: он едет в диагностическом событии, если оно настроено, и в лог таски не попадает никогда.

### Чего документация API не говорит

- **Квоты и частота запросов.** Не названы ни те, ни другая — поэтому `request_delay` по умолчанию равен консервативным 0,2 с и является параметром, а не константой.
- **Формат ошибки.** Спецификация описывает ответ на успешный запрос и больше ничего. Провайдер ищет отказ в трёх формах — `{"error": {…}}`, `{"errors": [{…}]}` и `{"code": …, "message": …}` на верхнем уровне — и сообщает найденные код и сообщение; для ответа, сформулированного иначе, `error_code` остаётся пустым.
- **Против чего на самом деле возражает `query_error`.** 400 со словами `Query is too complicated. Please reduce the date interval or sampling.` — отказ транзиентный, а не приговор запросу: одна и та же кампания за тот же день с теми же параметрами ответила за 641 мс и упёрлась в отказ одиннадцатью минутами позже, а каждый вариант того же запроса — меньше группировок, меньше метрик, другой `accuracy` — тоже получил ответ. Исход решает то, сколько эндпоинт отвечает в этот момент, и отказ приходит примерно на десятой секунде. Поэтому именно этот отказ повторяется, а его формулировка не принимается на веру.
- **Присылается ли когда-нибудь `Retry-After`.** Он соблюдается везде, где приходит, а где не приходит — решает лестница backoff.
- **Какие значения принимает `accuracy`.** `"full"` стоит по умолчанию потому, что альтернатива — цифры, плывущие между прогонами; словаря допустимых значений документация не приводит.
- **Какие поля лежат внутри значения группировки.** Гарантирован только `name`, а единственный пример в спецификации пустой. Именно поэтому значение едет тем объектом, каким пришло.

## Диагностика запросов в Loki (`loki_conn_id`)

Необязательна, по умолчанию выключена. С заданным `loki_conn_id` оператор отправляет по одному диагностическому событию на каждую HTTP-попытку к **обоим** эндпоинтам — списку кампаний и статистике — в [Loki](https://grafana.com/docs/loki/latest/). Событие описывает, как прошла попытка (уровень, исход, тайминг, HTTP-статус, форма сырого ответа, что отчёт сказал о собственных цифрах), запрос, каким он ушёл, и — для каждой попытки, чей ответ оказался невразумительным, — сырое тело ответа, так что прошедший прогон можно разобрать потом в Grafana. **Прочитайте [Политику содержимого](#политика-содержимого) прежде чем включать: на аномальном ответе тело уезжает таким, каким пришло, и считается произвольными чувствительными данными.**

Включение диагностики не меняет выгрузку: те же файлы, то же возвращаемое значение оператора, те же исключения с теми же типами и текстами. Недоступность Loki не может уронить таску — первая же неудача при отправке пишет один WARNING и выключает диагностику до конца этой таски. Единственная цена — время: отправка синхронная, с таймаутом 2 с на подключение и 3 с на чтение, поэтому неотвечающий Loki задержит попытку примерно на 5 с — один раз, до того как диагностика выключит себя сама. Половина, отвечающая за чтение, ограничивает тишину между полученными байтами, а не весь обмен, поэтому Loki, отвечающий по капле, способен задержать попытку дольше; используется только статус ответа, тело не скачивается. Чего диагностика не поглощает — это остановки самой таски: сработавший `execution_timeout` или пришедший SIGTERM прерывают таску тут же, а прерванная ими попытка остаётся неотправленной вместо того, чтобы задержать остановку на время отправки.

Прогон, упавший до первого запроса — коннекшна нет в Airflow, `extra` не называет рекламодателя, пароль пуст, — не отправляет ничего, поэтому отсутствие событий у `dag_run` ничего о нём не доказывает: оно читается так же, как выключенная диагностика или недоступный Loki.

```python
YandexAdmetricaStatsOperator(
    task_id="collect",
    admetrica_conn_id="yandex_admetrica_default",
    loki_conn_id="loki_default",   # необязателен; без него ничего не отправляется
    date="{{ params.date }}",
    dimensions=["am:e:placement"],
    metrics=["am:e:renders"],
)
```

Вне оператора тот же клиент можно передать хуку напрямую:

```python
from airflow_provider_yandex_admetrica.hooks.loki import LokiClient
from airflow_provider_yandex_admetrica.hooks.yandex_admetrica import AdmetricaHook

hook = AdmetricaHook(
    admetrica_conn_id="yandex_admetrica_default",
    loki=LokiClient(conn_id="loki_default", context={"dag_id": "adhoc"}),
)
rows = hook.get_stats("2026-08-20", ["am:e:placement"], ["am:e:renders"])
```

### Подключение к Loki

Создайте в Airflow подключение с `conn_type = http`:

| Поле в интерфейсе Airflow | Значение |
|---|---|
| **Host** | Базовый URL Loki — либо с явной схемой (`https://loki.example.ru`, порт допустим: `https://loki.example.ru:3100`), либо голый хост (`loki.example.ru`) в паре со **Schema**. Адрес IPv6 пишется в скобках: `[::1]`, `http://[::1]:3100` |
| **Schema** | `https` или `http`. Обязательна, когда в **Host** нет схемы |
| **Port** | Необязателен (например `3100`), применяется только когда в **Host** нет ни схемы, ни собственного порта |
| **Login** / **Password** | Необязательная Basic Auth. Задавайте оба поля или ни одного |

Путь `/loki/api/v1/push` дописывается автоматически; завершающий слэш в **Host** допустим, а **Host**, уже оканчивающийся этим путём, берётся как есть. `Host = https://loki.example.ru` и пара `Host = loki.example.ru` плюс `Schema = https` равнозначны.

Учётные данные живут в **Login**/**Password**, а не в URL: **Host** с userinfo (`https://user:token@loki.example.ru` — форма, которую публикует Grafana Cloud) отклоняется с WARNING, как и строка запроса, и фрагмент.

Схема никогда не угадывается. Голый **Host** при пустой **Schema** — это сломанный коннекшн: диагностика выключается с WARNING, называющим, что поправить, а не подставляет молча `http`. То же происходит при пустом **Host** и при любой схеме кроме http/https.

Basic Auth требует HTTPS: с заданным **Login** и не-HTTPS-адресом не отправляется ничего. Наполовину заполненные учётные данные (**Login** без **Password** или наоборот) считаются ошибкой конфигурации и тоже выключают диагностику.

Мультитенантный Loki не поддерживается — заголовок `X-Scope-OrgID` не отправляется. Приёмник должен быть однотенантным либо стоять за шлюзом, который сам проставляет тенанта.

Отправка считается доставленной только по HTTP 204 — статусу, которым отвечает Loki. Всё остальное — `200` от обратного прокси, редирект (редиректы не выполняются) — это неудача: один WARNING, и диагностика выключена до конца этой таски.

Каждая запись несёт единственную метку потока, `service="airflow-provider-yandex-admetrica"`, чтобы кардинальность меток оставалась постоянной. Всё прочее живёт в JSON-теле строки и запрашивается через LogQL по разобранному телу:

```logql
{service="airflow-provider-yandex-admetrica"} | json | outcome != "success"
```

Эта метка — собственная метка провайдера, поэтому запрос Grafana, отбирающий по `service`, увидит эти события только после того, как метку в него добавят; панели, построенные на общих для провайдеров полях — `level`, `outcome`, `http_status`, `duration_ms`, `attempt`, — работают без правок.

Поскольку метка одна и та же для всех тасок, все они пишут в один поток. На Loki, отвергающем записи не по порядку, у параллельных тасок отправка поэтому может получить 4xx, что выключит диагностику для этой таски.

| Поле | Описание |

Ограничен по каждому параметру отдельно: описываются не более 24 параметров, имя — до 40 символов, текстовое значение — до 300, каждый обрез помечен `…`. У запроса, несущего больше 24 параметров, появляется ключ `<params truncated>` с числом оставшихся за бортом. Имя — такой же выход из процесса, как и значение, поэтому проходит тот же маскирующий шлюз; два имени, которые граница сводит к одному тексту, различаются позицией параметра |

| `payload_kind` | Какой формы оказалось тело: `dict` (ключ строк на месте и держит обещанный список либо пустое значение другого типа), `rows_absent` (ключа строк нет вовсе), `rows_non_list` (ключ строк держит непустое значение, не являющееся списком), `non_dict` (само тело — не объект) |

Тип и сообщение схлопываются в одну строку, ограничиваются 300 символами и проходят через ту же точку маскирования, что и всё покидающее процесс. Заполняется для HTTP 200, из которого не прочитались строки, и для любого не-200, чьё тело называет ошибку |

Значение заголовка — текст, написанный сервером, поэтому проходит через ту же точку маскирования, что и всё покидающее процесс |

Набор ключей события постоянен: поле, которого попытка не определила, присутствует со значением `null`. `rows_count`, `rows_shape_ok` и `payload_kind` остаются `null` у любой попытки, не получившей разобранного тела HTTP 200, а собственные поля отчёта — от `total_rows` до `data_lag` — заполняются только из ответа, который их нёс.

#### Запрос, каким он ушёл

`request_method`, `request_url`, `request_headers` и `request_params` вместе — это шаблон запроса, а не дословная стенограмма провода. Разделяют их две вещи:

- **`Authorization` несёт маску**, `"OAuth y0__xC…9f2a"` — схема `OAuth ` сохранена, токен сведён к первым шести и последним четырём символам, соединённым через `…`. Токен короче двадцати символов — вдвое больше того, что показывает маска, — заменяется целиком на `***`, поэтому маска никогда не проговаривает бо́льшую часть значения. Значение собирается из схемы и маски, а не копируется и правится, так что сырой заголовок в событие не попадает вовсе. Маски хватает, чтобы отличить один токен от другого; повторить запрос — значит подставить живой.
- **Перечислены только заголовки, которые ставит провайдер.** Те, что `requests` добавляет от подключения, — `User-Agent`, `Accept-Encoding`, `Connection` — в событие не попадают: смысла запроса они не меняют.

`request_headers` и `request_params` — вложенные объекты. В LogQL `| json` разворачивает вложенность через подчёркивание, и запрашиваются эти поля так:

```logql
{service="airflow-provider-yandex-admetrica"} | json | level = "error"
{service="airflow-provider-yandex-admetrica"} | json | endpoint = "stat" and sampled = "true"
{service="airflow-provider-yandex-admetrica"} | json | line_format "{{.request_params_ids}} {{.response_body}}"
```

### Значения `outcome`

| Значение | Смысл |
|---|---|
| `success` | HTTP 200 с корректным ответом, в том числе пустым: «у этой кампании в этот день не было показов» — валидный ответ |
| `empty_shape` | HTTP 200, в котором не опознан список объектов-строк — попытка падает, что бы ни говорил `payload_kind` |
| `auth_error` | HTTP 401 или 403 — падает сразу, поскольку токен здесь никто не обновляет |
| `retryable_error` | HTTP 429, любой 5xx или 400, чьё тело называет `error_type: query_error`, — повтор, а на последней попытке падение. 429 и 5xx идут по лестнице 1 / 2 / 4 с, и названный ответом `Retry-After` соблюдается вместо её ступени, с потолком 300 с; повторяемый 400 идёт по собственной лестнице 5 / 15 / 45 с. Исход называет политику, а `http_status` вместе с `error_type` — факт, и по ним дашборд эти случаи и различает |
| `http_error` | Любой другой статус, кроме 200, — падает сразу |
| `network_error` | Запрос не завершился (таймаут, DNS, TLS, прокси) — повторяется как 5xx |
| `invalid_json` | HTTP 200, тело которого не разобралось |
| `unexpected_error` | Тело, являющееся валидным JSON, но не объектом (`["a", "b"]`), — попытка падает, называя `payload_kind=non_dict`, — и, как страховка, попытка, закончившаяся как-то иначе |

Повторяется весь диапазон 5xx, а не привычная четвёрка: прокси перед API отвечает кодами по собственному выбору, и каждый из них говорит, что запрос не дошёл до логики, которая отказала бы ему по существу.

`campaign_id`, `date` и `offset` говорят, чего стоил отказ. Запрос статистики, упавший на `offset = 1`, сломался до того, как по этой кампании что-либо собрано; дальше — пагинация сломалась посередине, и собранные до этого строки уходят вместе с таской, а не в частичный файл. Так или иначе таска краснеет, и это и есть сигнал для алерта: любой отказ роняет прогон, поэтому красная таска — это алерт, а файл на диске означает полную выгрузку дня.

### Уровень (`level`)

| `level` | Когда | Смысл |
|---|---|---|
| `info` | `success` | Ответ вразумителен — независимо от того, нёс он строки или нет |
| `warn` | `retryable_error` или `network_error`, когда попытка ещё осталась | Ситуация, которая может починиться сама; впереди повтор |
| `error` | `retryable_error` или `network_error` на последней попытке; `auth_error`; `empty_shape`; `http_error`; `invalid_json`; `unexpected_error` | Ответ невразумителен, в доступе отказано или запрос не завершился |

`level` отвечает на вопрос «вразумителен ли ответ и есть ли ещё надежда», а не «упала ли таска». Успешный ответ без строк — рутина: кампания без показов в конкретный день это обычное состояние большинства кампаний рекламодателя, — поэтому он остаётся `info`, а оговорки, которые успешный ответ способен нести, семплирование и скрытые строки, едут отдельными полями и предупреждениями в логе таски. `auth_error` — `error` с первого взгляда: токен долгоживущий, обновлять его здесь некому, и следующая попытка получила бы тот же отказ.

**Эта таблица заодно и политика выгрузки тела.** Тот же `level` решает и как событие выглядит в Grafana, и покидает ли сырое тело процесс (см. ниже). Перенос строки в этой таблице меняет то, какое содержимое уезжает, а не только цвет алерта.

### Сырое тело ответа

`response_body` держит текст ответа, ограниченный 32768 символами (константа провайдера — настройки в коннекшене или операторе для неё нет). Тело длиннее обрезается по этому бюджету и оканчивается на `…[truncated]`. Текст читается в той кодировке, которую сервер назвал в `Content-Type`, и как UTF-8, когда он не назвал никакой или назвал кодек, неизвестный Python. Не декодируемые байты заменяются, а не роняют тело целиком: нечитаемое тело стоит здесь меньше, чем тело, прочитанное по разумному предположению.

| Ситуация | `response_body` |
|---|---|
| `level = "info"` | `null` — диагностика намеренно не читает тело |
| Любой другой уровень, если байты ответа удалось прочесть | Текст ответа, ограниченный по длине, с вырезанным токеном |
| `network_error` — ответа нет | `null` |
| Ответ есть, но его байты не прочитались либо проговаривают токен так, что поиск до него не дотягивается | `null` |
| Диагностика выключена (`loki_conn_id` не задан) или таску останавливают | `null` — тело не читается и ничего не отправляется |

Ключ присутствует всегда; `null` в нём не обещает, что уровень был `info`.

В здоровом прогоне все события — `info`, так что ни одно тело не уезжает. Объём растёт на падающих прогонах и на ретраях: `retryable_error` и `network_error` с оставшейся попыткой — это `warn`, поэтому **каждая** неудачная попытка увозит своё тело — четыре штуки, когда шторм исчерпывает бюджет попыток одного запроса.

Одно событие — одна строка Loki, а Loki отвергает строку длиннее `limits_config.max_line_size` — по умолчанию 256 КБ. При всех ограниченных полях на своих потолках, теле из управляющих символов и параметрах из эмодзи — самых широких после экранирования в JSON — строка получается около 215 КБ, так что дефолт оставляет запас. Инсталляция, понизившая этот лимит, — Grafana Cloud, донастроенный self-hosted Loki — ответит на такую отправку не-204, и первый же такой отказ выключит диагностику до конца этой таски, ровно как любая другая неудача отправки. Проверьте `limits_config.max_line_size` на своём инстансе прежде чем включать.

### Политика содержимого

Сырое тело ответа покидает процесс всякий раз, когда ответ оказался невразумительным, то есть на любом `level` кроме `info` (см. таблицы выше). **Считайте его произвольными чувствительными данными.**

- **Тело без опознанных строк — не то же самое, что тело без чувствительного содержимого.** Ответ способен нести соц-дем разрезы, внутренние идентификаторы или секреты внутри объекта ошибки, не содержа при этом никакого списка строк, — и такое тело уезжает целиком.
- **Известный край:** аномальный исход рядом с опознанными строками увозит тело, содержащее сам отчёт.
- **Гарантия по токену покрывает все каналы.** OAuth-токен маскируется в `request_headers`, вырезается из `response_body`, а также из `error_type`, `error_message` и из текста каждого исключения этого модуля: сервер или прокси вправе отразить заголовок `Authorization` внутри JSON-поля `message`, и структурированное описание ошибки — такой же выход наружу, как сырое тело. Текст, который токен пережил, — ответ, проговаривающий его с чем-то между символами, как это делает UTF-16, прочитанный как UTF-8, — отбрасывается целиком, а не отправляется: значение важнее диагностики. Отказ непредвиденного рода — тот, чьи слова принадлежат ни этому модулю, ни сетевому слою, — уходит из запроса переформулированным так же: его называет тип, а его текст проходит тот же фильтр. Гарантия распространяется и на лог таски, чьи строки собраны из тех же замаскированных полей, и на трейсбек, который печатается вместе с отказом: исключение этого модуля не тащит за собой исходное исключение ни как причину, ни как контекст, потому что прицепленное исключение печатает под ним свои собственные, ничем не замаскированные слова.
- **Структурированные поля — это структура, а не граница.** `error_code`/`error_type`/`error_message` и `exception_message` — узкие, пригодные для запросов сводки; они описывают отказ, но не ограничивают то, что событие раскрывает, потому что рядом едет тело.
- **Настройки, которая оставила бы диагностику включённой, а тела внутри, не существует.** Что уезжает, решает таблица уровней; единственный способ прекратить выезд тел — не задавать `loki_conn_id`, то есть выключить возможность целиком.
- Заголовки ответа, кроме двух `X-RateLimit-*`, не копируются.
- Хранение и доступ следуют за Loki: тела живут столько, сколько их держит инстанс, и прочитать их может каждый, у кого есть общие учётные данные Loki.

Как собираются структурированные поля:

- Из отказа берутся только `code` (значение ровно типа `int`), `error_type` (значение ровно типа `str`, замаскированное и обрезанное так же, как сообщение) и `message` (значение ровно типа `str`, схлопнутое в одну строку, замаскированное и обрезанное до 300 символов). Значение неожиданного типа описывается своим типом — `<non-dict error: list>`, `<non-str error_type: int>`, `<non-str message: dict>` — а не сериализуется, так что вложенные ключи вроде `details` или `trace` в событие не попадают.
- `exception_message` заполняется только для `invalid_json` и только когда об отказе сообщил стандартный декодер JSON. Оно собирается из собственных атрибутов исключения, а не из его отрендеренного текста, и формулировка выбирается из фиксированного словаря литералов самого декодера — `Expecting value`, `Expecting ',' delimiter`, `Expecting ':' delimiter`, `Expecting property name enclosed in double quotes`, `Extra data`, `Unterminated string starting at`, `Invalid control character at`, `Invalid \escape`, `Invalid \uXXXX escape`, — за которой идёт позиция, отсчитанная в документе: `Expecting value: line 1 column 1 (char 0)`. Всё, что декодер сформулировал иначе, сообщается как `<other decoder message>` с той же позицией, потому что часть его сообщений формируется вокруг символа, взятого из документа. Отказ разбора любого другого происхождения записывает только `exception_type`, как и всякий иной исход.
- Из заголовков ответа копируются только два `X-RateLimit-*`, и только когда их тип — ровно `str`, с обрезкой до 32 символов. Значение любого другого типа описывается своим типом (`<non-str header: int>`), так что неизвестный объект в событие не отрисовывается никогда.
- Обрезка ограничивает длину, а не содержимое.

## Примеры

Полный боевой пример с загрузкой в S3 и BigQuery лежит в [`examples/`](examples/):

- [`admetrica_to_bq_and_s3_dag.py`](examples/admetrica_to_bq_and_s3_dag.py) — период, развёрнутый в mapped task group по дню на map index: сбор дня, обе выгрузки и загрузка в BigQuery лежат внутри индекса, поэтому упавший день не держит остальные, а повтор дня — это clear его map index вместе с задачами ниже. Снапшот справочника грузится один раз за прогон, отдельной группой после дней

Ему нужно больше, чем сам провайдер:

- `apache-airflow-providers-google` и `apache-airflow-providers-amazon` — этот пакет ставит их только в extra `dev`, так что инсталляция, запускающая DAG, ставит их себе сама
- коннекшены `yandex_admetrica_default`, `loki_default`, `google_cloud_default` и `aws_default`
- файловая система, общая для всех воркеров, на которых идут задачи DAG, примонтированная на каждом по пути `BASE_DIR`. `collect` пишет туда файл дня, а обе выгрузки и `cleanup` — отдельные экземпляры задач, которые его читают, тогда как привязки к воркеру внутри task group Airflow не обещает: на Celery или Kubernetes с локальными дисками выгрузки падают на отсутствующем файле, а собранные файлы остаются на том воркере, который их написал. Раскладка держится на однохостовом `LocalExecutor` либо на общем томе, примонтированном в `BASE_DIR`
- промежуточный бакет GCS: DAG создаёт его первой задачей, если его нет, — загрузка в BigQuery читает из GCS, а не с диска воркера, поэтому каждый файл сперва едет в бакет. Убирает его оттуда правило жизненного цикла на удаление через день: DAG добавляет его к тем правилам, что на бакете уже стоят, и ограничивает условием `matchesPrefix` — бакет может быть общим, и правило адресует только префикс этого DAG
