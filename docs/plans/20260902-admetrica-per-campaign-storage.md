# Гранула хранения «день × кампания»

## Overview

Единица перезаписи сейчас — день, и это записано в трёх местах сразу: оператор
пишет один `stats/<date>.json` на все кампании, ключ S3 адресуется днём и
перетирается `replace=True`, а BigQuery грузится `WRITE_TRUNCATE` в дневную
партицию таблицы `stats`.

Пока выгрузка была всегда полной, это было корректно: перезалив дня заменял
день целиком. С отбором кампаний выгрузка становится **частичной**, а перезапись
остаётся полной — и разница молча удаляется. Два сценария одного дефекта:
перезаливка выбранных кампаний стирает из витрины все остальные за те же дни;
сбор только активных за скользящее окно стирает кампанию, ушедшую в архив, хотя
в те дни она ещё крутилась.

План опускает гранулу перезаписи до «день × кампания» везде — в локальной
раскладке, в ключе S3, в промежуточном объекте GCS и в имени таблицы BigQuery.
После него частичная выгрузка перестаёт быть опасной по построению: задача
физически не может дотянуться до чужих данных.

Изменение ломающее — раскладка файлов, ключи и имена таблиц меняются.
Совместимость не поддерживается: провайдер нигде не применяется.

Этот план делается **до** `docs/plans/20260902-admetrica-campaign-selection.md`.

## Solution Overview

Одно решение проведено через все четыре слоя хранения: **адрес данных содержит
кампанию**. Всё остальное — следствия.

- **Оператор** пишет файл на кампанию и возвращает запись на кампанию. Строки
  раскладывает он сам, группируя по `row["campaign_id"]`; хук не трогается —
  `get_stats()` как отдавал плоский список, так и отдаёт.
- **S3** получает hive-партицию `_campaign_id=<id>` последней в иерархии ключа.
  Порядок такой, потому что дата — то, по чему фильтруют диапазоном, а кампания
  — чем сужают внутри. Ключ уже построен в hive-стиле (`_year=`, `_month=`,
  `_day=`, `_date=`), так что это продолжение принятой конвенции.
- **BigQuery** получает таблицу на кампанию: `stats_<adv>_<campaign>`. Гранула
  нужна двумерная, а BigQuery партиционирует по одному полю, поэтому второе
  измерение уходит либо в имя таблицы, либо в DML. Имя таблицы сохраняет
  `WRITE_TRUNCATE` — то есть идемпотентную декларативную загрузку без
  транзакций и без окна, в котором старое стёрто, а новое ещё не приехало.
- **DAG** сохраняет группу дня и грузит файлы дня циклом. Airflow запрещает
  маппинг внутри mapped-группы, поэтому либо группа дня, либо маппинг по
  кампаниям; группа дня выбрана ради конвейерности — свежий день доезжает до
  витрины, пока хвост периода ещё собирается.

Цена wildcard-таблиц принята сознательно: нет кэша результатов (каждый повтор
одного и того же запроса оплачивается заново), нет BI Engine, схемы всех таблиц
обязаны совпадать до типов и партиционирования. Читатели здесь — следующий слой
конвейера, а не дашборды, поэтому это не жмёт. Схема из пяти колонок стабильна
по построению: новые группировки и метрики живут внутри `dimensions` и
`metrics` типа JSON и схему не меняют.

Кампания, не давшая за день ни строки, не пишет ничего — ни файла, ни каталога,
ни строк. Её партиция в витрине не перезаписывается, и прежние цифры остаются:
это последние известные данные за тот день, а не мусор.

## Technical Details

### Раскладка и запись

| слой | адрес |
|---|---|
| локально | `<base_dir>/<dag>/<run>/<advertiser_id>/stats/<date>/<campaign_id>.json` |
| S3 | `{prefix}/{adv}/stats/_year=2026/_month=09/_day=01/_date=20260901/_campaign_id=1234/2026-09-01.json` |
| GCS | `{prefix}/<dag>/<run>/{adv}/stats/<date>/<campaign_id>.json` |
| BigQuery | `{project}.{dataset}.stats_{adv}_{campaign}${YYYYMMDD}` |

Словарь не меняется нигде: `dict/campaigns/<snapshot_date>.json`, ключ S3 без
`_campaign_id=`, таблица `campaigns` одна. Он снимок кабинета целиком, и его
перезапись целиком корректна.

День становится именем каталога, поэтому санация дня в `_build_path` остаётся в
силе для сегмента каталога. `campaign_id` не санируется: он приходит из
`_campaign_record`, где уже проверен как положительное целое, — то есть
единственный источник этого сегмента доверенный по построению.

Запись остаётся атомарной пофайлово: временный файл рядом и `os.replace` на
место. Целостность дня в целом держится на другом — `execute()` возвращает
список только дойдя до конца, поэтому упавшая на середине таска не отдаёт наверх
ничего, и загрузка не увидит полудня.

### `ExportRecord`

```python
class ExportRecord(TypedDict):
    kind: str
    date: str
    path: str
    advertiser_id: int
    campaign_id: int | None    # кампания для kind="stats"; None для kind="dict"
```

`TypedDict` тотальный, поэтому ключ обязателен у **обеих** разновидностей
записи: `_export_campaigns` кладёт `campaign_id=None` явно. Без этого любой
`record["campaign_id"]` в DAG уронит словарную ветку `KeyError`, и обнаружится
это только на живом прогоне.

`execute()` возвращает список «N записей `stats` + одна `dict`». Записи `stats`
идут в порядке кампаний обхода, то есть в порядке списка кабинета.

### Загрузка в DAG

Группа `day` сохраняется. Внутри неё вместо оператора на день — `@task`,
которая перебирает записи `kind="stats"` и грузит каждую:

- **S3**: `S3Hook.load_file(filename=…, key=…, bucket_name=…, replace=True)`;
- **BigQuery**: `GCSHook.upload(bucket_name=…, object_name=…, filename=…)`, а
  затем `BigQueryHook.insert_job(configuration=…)` — метода `run_load` в
  провайдере нет. Конфигурация:

```python
configuration={"load": {
    "sourceUris": [f"gs://{GCS_BUCKET}/{gcs_object}"],
    "destinationTable": {"projectId": …, "datasetId": …,
                         "tableId": f"stats_{adv}_{campaign}${yyyymmdd}"},
    "schema": {"fields": BQ_STATS_SCHEMA},
    "autodetect": False,
    "sourceFormat": "NEWLINE_DELIMITED_JSON",
    "writeDisposition": "WRITE_TRUNCATE",
    "createDisposition": "CREATE_IF_NEEDED",
    "timePartitioning": {"type": "DAY", "field": "date"},
}}
```

`job_id` не задаётся: `insert_job` подмешивает микросекунды, поэтому ретрай не
упирается в 409, и идемпотентность держится на этом вместе с `WRITE_TRUNCATE`.

Хуки импортируются **на уровне модуля** примера, как уже импортирован
`GCSHook`: существующие тесты подменяют именно атрибут модуля, и без этого
заявленные тесты «таска грузит столько файлов, сколько записей» не пишутся.

В совмещённом примере направления остаются **двумя параллельными тасками** —
цикл S3 и цикл GCS+BQ, — как сейчас `upload_s3` и `upload_gcs >> load_bq`.
Одна таска на оба направления уничтожила бы независимость направлений, которую
план сам же требует сохранить.

День без записей `kind="stats"` поднимает `AirflowSkipException`, как это
делает сегодня `day.params`. На этом держатся `trigger_rule="none_failed"` у
`cleanup` и абзац `doc_md` про день без строк, поэтому поведение сохраняется
дословно, а не переизобретается.

Загрузка словаря остаётся отдельной группой `dictionary` и отдельным
декларативным оператором — запись там одна на прогон.

`find_record(records, "stats")` больше не годится для статистики: записей
несколько. Рядом заводится отбор всех записей вида — по одинаковой чистой
функции в каждом из трёх примеров, по существующей конвенции самодостаточности
примеров. Для словаря `find_record` остаётся.

Группа дня отдаёт наверх весь список записей, как и сейчас, а
`dictionary_record()` находит в нём снапшот справочника. Значение XCom одного
дня растёт с числом кампаний, но растёт оно у `day.collect`, который пушит свой
результат независимо от того, что возвращает группа, — и упирается в LONGBLOB, а
не в узкий предел: `map_index` входит в первичный ключ XCom, поэтому день лежит
своей строкой, а не складывается с остальными в одно значение.

### Цена одного load job на кампанию

Сегодня день — один load job. Станет — один на кампанию, последовательно внутри
одной таски. Для рекламодателя из README на 70 кампаний это 70 выгрузок в GCS и
70 `insert_job` с ожиданием под `execution_timeout=2h`, а годовой бэкфилл — уже
десятки тысяч job'ов. С отбором активных кампаний (следующий план) обычный
прогон вернётся к единицам, но `campaign_scope="all"` на бэкфилле упирается
именно в это.

Решение: оставить последовательный цикл, но записать цену и проверить её на
живом бэкфилле. Лимиты BigQuery на load jobs считаются и на таблицу, и на
проект — при таблице на кампанию первый практически недостижим, второй нужно
сверить перед годовым перезаливом.

### Ограничение именования в BigQuery

Вью, чьё имя попадает под `stats_*`, ломает wildcard-запрос целиком — «If the
wildcard table matches any view in the dataset, the query returns an error even
if your query contains a `WHERE` clause on the `_TABLE_SUFFIX` pseudocolumn».
Вью следующего слоя держать в другом датасете либо называть не на `stats_`.
Коллизии префиксов при этом нет: `stats_1234_5` не попадает под `stats_123_*`,
потому что после `123` стоит `4`, а не `_`.

## Post-Completion

*Items requiring manual intervention or external systems - no checkboxes, informational only*

**Разовая уборка перед первой выгрузкой в новой раскладке**:
- в существующих каталогах `_date=…/` на S3 лежит старый `<day>.json` со
  строками всех кампаний. Новые файлы лягут в подкаталоги рядом, и движок,
  читающий префикс, увидит и то и другое — каждая строка задвоится. Старые
  дневные объекты нужно удалить или перенести в архивный префикс **до** первой
  выгрузки;
- у читателя S3 появляется новый ключ партиции `_campaign_id`: внешнюю таблицу
  или краулер придётся переопределить, иначе новый уровень не будет прочитан;
- в BigQuery старая таблица `stats` остаётся с историей: либо перелить её в
  таблицы по кампаниям (`INSERT` с группировкой по `campaign_id`), либо вывести
  из употребления;
- проверить, что в датасете нет вью, попадающей под `stats_*`, и что вью
  следующего слоя живут в другом датасете.

**Правка плана отбора кампаний**:
- после этой работы `docs/plans/20260902-admetrica-campaign-selection.md`

  закладывался защитой ровно от стирания партиции при `WRITE_TRUNCATE`. Вернуть
  умолчание примеров к `"active"`, снять обоснование про перезалив партиции и
  поднять версию того плана до `0.4.0`.
