# Повторы для HTTP 400 `query_error` и точность диагностики отказов

## Overview

Отчётный эндпоинт AdMetrica отвечает с большим разбросом времени и, не уложившись
примерно в десять секунд, отдаёт HTTP 400 с текстом
`Query is too complicated. Please reduce the date interval or sampling.`
Провайдер считает 400 окончательным отказом, поэтому одна такая кампания роняет
таску целиком, а ретрай Airflow пересобирает день заново — все сотни кампаний,
с теми же сотнями шансов споткнуться.

План делает этот отказ повторяемым на уровне одного запроса и попутно закрывает
четыре расхождения между тем, что провайдер делает, и тем, что он о себе говорит.

**Что это даёт.** При одном проценте отказов на запрос и трёхстах кампаниях
вероятность довести прогон до конца поднимается с 14 % (три полных прогона
Airflow) до 99.9997 % (четыре попытки на запрос).

Вторая цифра — верхняя граница, взятая в предположении, что попытки падают
независимо. Наблюдаемый дрейф идёт на масштабе минут, а лестница укладывается в
65 секунд, то есть внутрь этого масштаба, — значит попытки коррелированы и
реальная величина ниже. Насколько — покажет доля `retryable_error` в Loki после
выкатки.

**Что установлено опытом, а не догадкой.** Отказ транзиентный: кампания 56904 за
2025-08-20 ответила за 641 мс в 15:26 и упёрлась в дедлайн в 15:37 с теми же
параметрами. Лестница из семи запросов и замеры 4 × 10 по кампании 81144 вернули
200 на всех вариантах запроса, включая точную копию того, что шлёт провайдер, —
значит запрос корректен, а отказ зависит от момента. Ни `accuracy`, ни число
группировок и метрик на исход не влияют.

## Solution Overview

**Классификация вместо статуса.** Сейчас решение о повторе принимается по коду
ответа: `_RETRY_STATUSES` содержит 429 и весь 5xx. Для 400 кода недостаточно —
повторять нужно только `query_error`, а не любую ошибку разбора запроса. Значит
тело отказа надо прочитать **до** решения о повторе, и `error_type` становится
частью классификации, а не только частью отчёта.

**Исход `retryable_error`, а не новый.** Повторяемый 400 получает тот же исход,
что 429 и 5xx. Это не косметика: `_event_level` (`:1254`) выдаёт `warn` для
непоследних попыток исходов из `_RETRIED_OUTCOMES` и `error` для последней —
ровно то поведение, которое требуется в Loki. Если оставить `http_error`,
каждая попытка ушла бы как `error`.

Отличать этот отказ от 503 дашборд будет по `http_status` и по новому
`error_type`: `outcome` называет политику («это мы повторяем»), а статус и тип —
факт.

**Своя лестница.** Дрейф идёт на масштабе минут, а `[1, 2, 4]` укладывается в
семь секунд, то есть целиком в одно плохое окно. Для `query_error` — отдельная
`[5, 15, 45]`, размах 65 секунд. Обычные 429 и 5xx остаются на прежней: у них
другая природа, а 429 и так слушается `Retry-After`.

**Почему это не разгоняет стоимость прогона.** Запрос, исчерпавший попытки,
роняет таску. В настоящей аварии таска умирает на первой же кампании, а не
перебирает триста штук по 65 секунд. Платим только за кампании, которые в итоге
прошли: при одном проценте отказов на триста кампаний это около трёх повторов,
секунд двадцать на прогон.

## Technical Details

**Новое поле события** (`schema_version` 1 → 2):

```json
{"schema_version": 2, "error_code": null, "error_type": "query_error",
 "error_message": "Query is too complicated. Please reduce the date interval or sampling."}
```

`error_code` остаётся пустым для таких ответов и это правильно: `_find_error`
берёт `errors[0]`, а там `code` нет — он лежит на верхнем уровне тела. Поле
`error_type` заполняет ровно эту дыру.

**Константы:**

```python
_BACKOFF_DELAYS      = [1, 2, 4]     # 429, 5xx, отказ сети
_QUERY_ERROR_DELAYS  = [5, 15, 45]   # HTTP 400 с error_type query_error
_AUTH_STATUSES       = frozenset({401, 403})
_RETRYABLE_ERROR_TYPES = frozenset({"query_error"})
```

**Инвариант, который обязан быть под тестом:** обе лестницы одной длины.
`max_attempts` считается как `len(_BACKOFF_DELAYS) + 1`, и лестница другой длины
рассогласовала бы номер попытки с индексом ступени.

**Порядок в ветке `else` у `_request_page`.** Тело читается до решения:

```python
else:
    _stamp_response_error(event, resp, token)
    if resp.status_code == 400 and event["error_type"] in _RETRYABLE_ERROR_TYPES:
        event["outcome"] = "retryable_error"
        if last_attempt:
            raise _MaskedError(...)
        retry_delay = _QUERY_ERROR_DELAYS[attempt]
    else:
        event["outcome"] = "http_error"
        raise _MaskedError(...)
```

**Строка лога.** Дробь `attempt N/M` осмысленна только там, где лестница
применима, то есть для исходов из `_RETRIED_OUTCOMES`. Для остальных строка
называет окончательность:

```
AdMetrica stat campaign_id=50158 date=2026-08-23 offset=1: failed, not retryable — HTTP 400, invalid_parameter, ...
```

**Строка о восстановлении** пишется в `finally` у `_request_page`, когда исход
`success` и попытка не первая. На первой удачной попытке не пишется ничего, так
что здоровый прогон лог не меняет:

```
AdMetrica stat campaign_id=75098 date=2026-08-23 offset=1: recovered on attempt 3/4
```
