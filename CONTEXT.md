# Domain & Architecture Context — airflow-provider-yandex-admetrica

## Domain concepts

| Термин | Значение |
|---|---|
| **Рекламодатель** (`advertiser_id`) | Владелец медийных кампаний в AdMetrica. Единица коннекшена: один Airflow connection = один рекламодатель. Живёт в `conn.extra` как `{"advertiser_id": 17004}`, читается `parse_connection`, отдаётся наружу свойством `AdmetricaHook.advertiser_id`. Число попадает в каждую запись файла, в ключ S3 и в имя таблицы статистики `stats_{advertiser_id}_{campaign_id}`, где стоит рядом с кампанией. |
| **OAuth-токен** | Секрет коннекшена. Живёт в `conn.password` **без** префикса `OAuth `; в заголовок уходит как `Authorization: OAuth {token}`. Долгоживущий: механизма обновления в провайдере нет, поэтому 401 и 403 — окончательный отказ. |
| **Кампания** (`campaign_id`) | Медийная кампания рекламодателя. Разрез статистики: API не умеет группировать по кампании и суммирует кампании, перечисленные в `ids`, поэтому кампания — единица запроса. Она же вместе с днём составляет гранулу хранения: файл, ключ S3, объект GCS и таблица BigQuery адресуют день одной кампании. |
| **Группировка** (dimension) | Разрез отчёта, имя вида `am:e:placement`. В ответе приходит объектом со свободным набором строковых ключей, из которых описанием гарантирован только `name`. |
| **Метрика** (metric) | Измеряемая величина, имя вида `am:e:renders`. В ответе приходит числом в массиве, позиция в котором — единственная связь значения с именем. |
| **Строка отчёта** | Элемент массива `data` ответа `/v1/stat/data`: `{"dimensions": [...], "metrics": [...]}`. Отчёт агрегирован по запрошенным группировкам, поэтому внутри одного ответа комбинация их значений строку именует. |
| **Запись статистики** | Каноническая форма строки, которую производит `_map_row`: плоские `date`, `advertiser_id`, `campaign_id` плюс два вложенных объекта `dimensions` и `metrics`. |
| **Служебные поля** | `date`, `advertiser_id`, `campaign_id` — плоские и типизированные, набор фиксирован кодом. `date` проставляет провайдер: отчёт запрашивается как `date1=date2=<день>` и о дне ничего не сообщает. |
| **Переменная часть записи** | `dimensions` и `metrics`. Набор ключей внутри них задаётся запросом, набор полей внутри значения группировки — ответом. Схема таблицы их не описывает: это JSON-колонки. |
| **Словарь кампаний** | Плоские записи management API — `campaign_id`, `name`, `status`, `date_start`, `date_end`, `advertiser_id`, `advertiser_name` (`_CAMPAIGN_FIELDS`), в фиксированном порядке и без переименований. |
| **Снапшот словаря** (`snapshot_date`) | Дата, на которую снят словарь. Management API отдаёт только текущее состояние справочника, поэтому снапшот датируется днём выгрузки, а не обрабатываемым днём. |
| **День** | Единица работы оператора. Период разворачивает DAG, каждый день едет отдельным map index: отказ дня не трогает соседние, повтор дня — clear его map index. |
| **`connection.extra`** | JSON поля *Extra* коннекшена. Единственная валидная форма — `{"advertiser_id": <положительное целое>}`. Ничего другого оттуда не читается. |
| **Диагностическое событие** | Dict с постоянным набором ключей (`_SCHEMA_VERSION` = 2), описывающий одну HTTP-попытку. Уходит в Loki одной строкой; локальным аналогом служит строка в логе таски. |
| **Ключ строки отчёта** | Проекция значений группировок строки на хешируемый кортеж (`_row_key`). Множество ключей живёт в пределах одной кампании. |

## API

Хост `https://api.media.metrika.yandex.net`, оба метода — GET. Отчётный
`/v1/stat/data` доступен только на тарифе Метрика Про.

`_ENDPOINT_URLS` — единственное место, где метка эндпоинта (`campaigns`, `stat`)
сопоставлена адресу, а `_ROWS_KEYS` — ключу, под которым эндпоинт кладёт строки
(`campaigns` и `data` соответственно). Первым аргументом `_request_page` идёт метка,
а не URL: и запрос, и описывающее его событие берут адрес из одной таблицы, поэтому
назвать разные эндпоинты они не могут.

Спецификация описывает только ответ 200. Формат тела ошибки, коды ошибок, квоты, RPS,
наличие `Retry-After` и допустимые значения `accuracy` не документированы — всё
поведение при отказе является конвенцией провайдера.

Наблюдением установлена одна форма тела отказа:

```json
{"errors":[{"error_type":"query_error","message":"…"}],"code":400,"message":"…"}
```

`error_type` лежит внутри объекта ошибки, а `code` — на верхнем уровне рядом с ним,
поэтому `_find_error` берёт `errors[0]`, и `error_code` для такого ответа остаётся
пустым: род отказа называет `error_type`.
Из его значений наблюдались `query_error` и `invalid_token`.

`query_error` транзиентен: одна и та же кампания за тот же день с теми же параметрами
отвечает то за сотни миллисекунд, то отказом, и приходит он примерно на десятой секунде
ответа. Ни `accuracy`, ни число группировок и метрик на исход не влияют, так что слова
отказа про сложность запроса наблюдаемому не соответствуют — повторяется он именно
поэтому.

Два эндпоинта считают `offset` по-разному, и это записано двумя константами:
`/v1/management/campaigns` пропускает строки и потому отсчитывается с 0, а
`/v1/stat/data` их нумерует и отсчитывается с `_STAT_OFFSET_BASE = 1`. Обход,
считающий с нуля, вернул бы первую строку отчёта дважды.

## Key seams (architectural boundaries)

### `parse_connection(extra: dict) -> int | None`

Модульная функция в `hooks/yandex_admetrica.py`. Единственная точка знания о форме
`extra`. Best-effort: не бросает исключений никогда, `None` означает «коннекшн не
называет пригодного рекламодателя», а решение, что с этим делать, принимает
вызывающий. WARNING называет **тип** непригодного значения, а не само значение:
`extra` — свободное поле, и секрет, вставленный не в тот ключ, не должен попасть в
лог таски из-за опечатки в имени ключа.

Возвращается сам `advertiser_id` — единственное, что коннекшн хранит в `extra`.
Токен лежит в `password` и через `parse_connection` не проходит.

### `_token_from_password(password) -> str | None`

Точка знания о форме пароля. Значение, записанное со схемой впереди, называет тот же
токен: схема снимается здесь, чтобы исходящий заголовок писал её ровно один раз —
удвоенная схема получает 401 и читается как мёртвый токен, а не как иначе заполненный
коннекшн.

### `AdmetricaHook._request_page(endpoint, params, event_fields) -> dict`

Единственное место, где делается HTTP-запрос, и оно ничего не знает о циклах над
собой: кампания, день и страница приходят как `params` для отправки и `event_fields`
для именования запроса в событии.

Внутри одной попытки: пауза `request_delay` перед серией (`_pace`), сам `requests.get`
с `_REQUEST_TIMEOUT`, классификация ответа, ровно одно событие и, для неуспешной
попытки, ровно одна строка в логе таски. Форм у этой строки две, и выбирает их
`_RETRIED_OUTCOMES`: исход из этого набора тратит ступень бюджета, поэтому строка
считает её (`attempt N/M failed`), а любой другой заканчивает выгрузку на месте, и
строка называет окончательность (`failed, not retryable`). Страница, вернувшаяся не с
первой попытки, добавляет к ним одну INFO-строку о восстановлении.

Тело HTTP-200 проверяется одним вопросом — является ли значение под ключом строк
списком объектов. Только такое тело возвращается вызывающему (пустой список кампании
без показов включительно); любое другое заканчивает попытку исключением, называющим
`payload_kind`. Ноль, который провайдер не смог прочитать, никогда не выдаётся за ноль,
о котором отчитался API.

Решение о продолжении принимается по **значению, которое вернули** `_classify_payload`
и `_stamp_response_error`, а не по полю события: чтение события обратно сделало бы схему
диагностики частью поведения выгрузки, и правка набора полей правила бы то, что
провайдер делает. `_stamp_response_error` возвращает `error_type` таким, каким его
написало тело, а в событие кладёт копию, прошедшую шлюз маскирования: политика читается
по слову API, поэтому усечение или вымарывание текста на выходе решение не двигает.

Отправка события и запись строки лога живут в `finally` под двумя независимыми `try`,
и строка пишется первой. Отказ любой половины роняет только её саму, с DEBUG-строкой,
называющей тип: `Wording the task-log line raised …; the line is dropped` и `Pushing the
event raised …; the event is dropped`. Порядок держит строку: `LokiClient.push` по
устройству пропускает наружу остановку таски, и остановка, пришедшая посреди push,
уносит с собой весь `finally`, — строка к этому моменту уже написана. Исключение в
полёте не подменяется никогда. Прерывание таски отмечает там же локальный флаг
`interrupted = not isinstance(e, Exception)`, который читает `finally`: при нём push не
делается, потому что отправка задержала бы остановку на своё время.

### `AdmetricaHook.get_campaigns() -> list[dict]`

Пагинация management API с явными `limit` и `offset`. Параметр `status` не передаётся
вовсе: архивная кампания крутилась в прошлом, её статистика так же реальна, как у
активной, и фильтр здесь молча укорачивал бы каждую перезаливку прошлого периода.

Останов — только по короткой странице; собранное число сверяется с `total` после
цикла, и расхождение роняет таск. `total` читается с каждой страницы и обязан быть
целым (`_declared_total` признаёт только целое) и одним и тем же: ответ без читаемого
итога оставляет сверку без опоры, сменившийся итог даёт два ответа о длине списка, и
оба случая роняют выгрузку.

Список кэшируется на время жизни хука: статистика и словарь одного прогона — два
читателя одного ответа.

`snapshot_date` хук не проставляет — см. «Единственный владелец `snapshot_date`».

### `AdmetricaHook.get_stats(...)` → `_report_params` → `_collect_campaign`

Три уровня с раздельными обязанностями:

- `get_stats` проверяет формат дня (`check_date`), документированные лимиты и
  зарезервированные ключи **до первого запроса**, берёт список кампаний и склеивает
  результат. Проверки, называющие значение вызывающей стороны, описывают его типом и
  длиной, а не цитируют: значение приходит снаружи, а текст отказа уходит в лог таски
  и в traceback.
- `_report_params` строит ту часть запроса, которая одинакова для всех кампаний, и
  строит её один раз, поэтому отчёт не может отличаться от кампании к кампании.
  Незаданный параметр в запрос не попадает — так спрашивается дефолт самого API.
  Слияние однонаправленное: `extra_params` добавляет имена, которых в запросе ещё нет,
  и не переопределяет ничего (`params.setdefault`).
- `_collect_campaign` обходит страницы одной кампании за один день: свой `offset`, своё
  множество ключей строк, своя сверка с `total_rows`. Останов — по короткой странице,
  а `total_rows` и `total_rows_rounded` читаются с каждой страницы и обязаны быть
  читаемыми: без них полнота дня не подтверждается ничем.

`sort` уходит перечислением всех запрошенных группировок. О порядке строк при
постраничном обходе документация API не говорит ничего, поэтому перечисление
группировок — собственная страховка хука, а не следствие описанного поведения: отчёт по
ним агрегирован, и комбинация их значений задаёт полный порядок над строками, тогда как
при сортировке по метрике длинный хвост площадок с `renders=1` API расставляет как ему
угодно, и строки переезжают между страницами прямо во время обхода.

Страховка подпёрта проверками: детектор повторов ключа строки внутри кампании и сверка
собранного с `total_rows` (`_check_row_total`) ловят разъехавшиеся страницы, поэтому
нестабильный порядок означает упавший день, а не дырку в данных. Щель — при
`total_rows_rounded` сверка смягчается до WARNING, и расхождение стерегут детектор
повторов и WARNING о сменившемся под обходом объявленном итоге.

### `_normalize_name(name, extra_params) -> str`

Одно правило на группировки и метрики, потому что API именует их одинаково: снимается
префикс `am:e:`, подставляется значение параметра вместо `<goal_id>` / `<currency>`,
camelCase переводится в snake_case.

Ключ — публичный контракт: его пишет аналитик в `JSON_VALUE(dimensions, '$.device_type')` и
он же стоит рядом с каждым именем в `docs/metrics-and-dimensions.md`. Смена правила
переименовывает колонки во всех файлах, записанных после смены, оставляя прежние под
старыми именами, а запрос по старому ключу отвечает NULL, а не падает.

### `_map_row(...) -> dict`

Чистая функция: читает аргументы и возвращает dict, без сети и без коннекшена. Форма
записи решается в одном месте и проверяется без окружения.

Ключи записи считает `_record_keys` — один раз на запрос, до цикла по кампаниям, потому
что имена и `extra_params` одинаковы для каждой строки каждой кампании дня. Оба
предупреждения об этой конфигурации — неотвеченная подстановка и два имени на одном
ключе — живут там же и выпадают по разу на выгрузку, а регулярки `_normalize_name` не
работают на каждой строке.

`_row_values` достаёт список из строки, `_named_values` спаривает готовые ключи со
значениями **по позиции** — ответ имён не называет, и позиция единственное, что связывает
число с метрикой. Строка другой длины непрочитываема: часть ключей осталась бы пустой
либо часть значений была бы выброшена, а в `total_rows` такая строка входит наравне с
целой — сверка полноты прошла бы, и файл выглядел бы целым. Поэтому такая строка роняет
день, называя кампанию, дату и оба числа.

Пустое значение записывается таким, каким пришло, на обеих половинах. Метрика, которая
делит или считает цену (`am:e:ctr`, `am:e:cpm`, `am:e:cpc`, `am:e:cpa<goal_id>`,
семейства `video*Percent` и `am:e:ecommerce<currency>Revenue`), пуста везде, где нет её
знаменателя или её стоимости, поэтому отчёт из одних таких метрик отвечает строками из
пустых чисел; пустое значение группировки — ровно то, что просит
`include_undefined`. И то и другое доезжает до записи как `None` и пишется как JSON
`null`, который BigQuery читает как NULL.

Порядок ключей фиксирован: служебные, затем группировки в порядке параметра, затем
метрики в порядке параметра. Файлы одного запроса при этом побайтово сравнимы, и
перевыгрузка читается как diff.

Поля **внутри** значения группировки не трогаются: это собственные слова API о том, что
группировка сматчила.

### `_row_key(raw_row) -> tuple`

Проекция строки на её идентичность. Задана явно, а не отдана самим объектам: значения
группировок — dict, в множество их не положить. Каждая группировка даёт пару из пометки и значения:
`("id", <id>)`, если под `id` пришло значение, иначе `("name", <name>)` — спецификация
гарантирует только `name`, и `id` со значением `null` говорит ровно столько же, сколько
отсутствующий, а различает такие строки имя; группировка без обоих —
`("raw", <строка всего объекта>)`, **и пометка входит в ключ**: площадка с `id=1` и площадка с именем `"1"` дублем не считаются, и
две площадки с одинаковым именем и разными `id` — тоже.

### `_new_event(...)` / `_event_level(event)` / `_emit_event(loki, event, resp, token)`

`_new_event` — единственное место, где перечислен набор полей схемы. Поля, которых
попытка ещё не определила, стартуют как `None`, поэтому набор ключей отправленного
события постоянен независимо от того, что случилось с запросом.

Заголовки и параметры строятся здесь же, а не проставляются позже: значение
`Authorization` собирается заново из схемы и маски (`_redact`), поэтому сырое значение
заголовка в событие не входит вообще, что бы с запросом дальше ни произошло.

`_event_level` отвечает на вопрос «читаем ли ответ и есть ли ещё надежда», а не «упал ли
таск»: `success` → `info`; повторяемый исход (`_RETRIED_OUTCOMES`) при оставшихся
попытках → `warn`; всё остальное → `error`. Отказ авторизации — `error` сразу: токен
долгоживущий и обновлять его здесь некому.

Та же таблица является политикой содержимого: событие уровня `info` держит тело внутри
процесса, всё остальное уходит вместе с `response_body`. **Перенос строки этой таблицы
меняет не окраску в Grafana, а состав того, что покидает процесс.**

`_emit_event` спрашивает у стока `enabled` до того, как что-то заполнять: сток с
сработавшим circuit breaker выбрасывает событие на входе, и платить за декодирование
тела для него незачем. Вопрос задаётся здесь, а не на месте вызова: сток отвечает на
него собственным кодом, а этот код выполняется с исключением в полёте.

### `_scrub(text, token, *, cut=False)`

Единственная дверь, через которую текст покидает процесс. Через неё проходят заголовки
запроса, тело ответа, сообщение сервера об ошибке и текст исключения — токен едет в
заголовке, и любой из этих каналов способен принести его обратно. Одна дверь означает
одно место, которое надо прочитать, чтобы знать, что канал может нести, а канал,
добавленный позже, наследует гарантию самим фактом вызова.

`None` означает «текст ехать не должен»: либо это не `str`, либо токен пережил поиск.
Пережить его он может, если между его символами что-то стоит — UTF-16, прочитанный как
UTF-8, оставляет между символами NUL, — и тогда значение важнее диагностики.

### `LokiClient.push(event)`

`hooks/loki.py`. Единственный выход диагностических событий из процесса, метка потока
одна — `service=airflow-provider-yandex-admetrica`, всё остальное живёт в теле строки,
поэтому кардинальность меток постоянна.

Best-effort по устройству: тело целиком в одном `try/except Exception`, потому что
вызов приходит из `finally`, где raise подменил бы исключение в полёте. Первый отказ
любого рода — непригодный коннекшн, неполные учётные данные, сетевая ошибка,
неожиданный статус — пишет один WARNING и выключает клиент до конца жизни (circuit
breaker): недоступный Loki стоит одного таймаута на таску, а не одного на HTTP-попытку.
Читается только статус ответа: push уходит со `stream=True` и закрывается, поэтому
большое или медленное тело отбрасывается на сокете.

Прерывания самой таски (`KeyboardInterrupt`, `SystemExit`, `AirflowTaskTimeout`,
`AirflowTaskTerminated` — все от `BaseException`) сквозь этот guard проходят: они
означают, что таску останавливают, а не что отказал Loki.

Не потокобезопасен намеренно, как и остальное состояние хука: один прогон оператора
конструирует один клиент и пишет через него последовательно.

### `YandexAdmetricaStatsOperator`

`_build_path` — единственное место, где складывается локальный путь; DAG и прогон в нём
есть, оба сегментами `id_segment`. У статистики день называет каталог, а файл внутри
назван кампанией; путь справочника кампании не знает и оканчивается датой снимка.
`execute` раскладывает плоский список хука по `campaign_id` — хук отдаёт день
целиком, а файлы из строк делает оператор. `_write` — JSONL, объект на строку,
`ensure_ascii=False`; запись атомарна пофайлово, а целостность дня держится на том, что
`execute` возвращает список, только дойдя до конца.
`_build_loki_client` — диагностика opt-in: пустой `loki_conn_id`, включая шаблон,
отрендерившийся пустым, не конструирует ничего.

`_snapshot_date` берёт день из `dag_run.start_date`, а не из часов машины: прогон, у
которого дни разложены по map index, может пересечь полночь, и часы дали бы два
снапшота в двух партициях от одного прогона. При отсутствующем `start_date` берётся
текущее время UTC.

`_export_campaigns` — единственное место, где на запись ставится `snapshot_date`.

`ExportRecord` — форма, которой оператор описывает записанный файл соседним таскам:
`{kind, date, path, advertiser_id, campaign_id}`. `advertiser_id` едет в записи, потому
что DAG строит по нему ключ S3 и имя таблицы, а взять его больше неоткуда: рекламодатель
назван в коннекшене, а коннекшн открывает только хук. `campaign_id` называет кампанию,
чьи строки лежат в файле, и им же адрес достаёт до одной кампании одного дня; у записи
справочника он `None` — снимок кабинета не принадлежит ни одной кампании. `TypedDict`
тотальный, поэтому ключ проставлен явно у обеих разновидностей: иначе `record["campaign_id"]`
в DAG ронял бы словарную ветку `KeyError`, и нашлось бы это только на живом прогоне.

`execute` возвращает список «запись на каждую кампанию, давшую строки, плюс одна запись
справочника». Записи статистики идут в порядке обхода кампаний, то есть в порядке списка
кабинета.

## Id sanitisation rule

`re.sub(r"[^\w-]", "_", raw)` — любой символ вне `[A-Za-z0-9_-]` становится
подчёркиванием. В `YandexAdmetricaStatsOperator._build_path` этой заменой получается
сегмент дня: день — шаблонное поле, которое заполняет параметр DAG, поэтому сегмент из
него не должен уметь адресовать файл вне `base_dir`. Формат дня проверяется в `execute`
вызовом `check_date` — той же функции, которой день проверяет `AdmetricaHook.get_stats`,
поэтому определение одно.

`id_segment(identifier)` — та же замена плюс дефис и первые восемь символов SHA-1
идентификатора. Ею получаются сегменты DAG и прогона: `run_id` несёт временную метку с
двоеточиями и плюсом, и сегмент каталога из неё должен получаться на любой файловой
системе, а дайджест оставляет различимыми идентификаторы, которые замена делает
одинаковыми. Читаемая часть обрезается по байтам до `_SEGMENT_BYTES` минус дайджест и
дефис: `NAME_MAX` равен 255 байтам, Airflow принимает идентификаторы до 250 символов, а
символ вне ASCII занимает больше байта. Функция публичная — тот же путь складывает `cleanup` в примере DAG, и
собирается он ровно из неё, а не из повторённого правила.

DAG в пути наравне с прогоном потому, что `run_id` уникален в пределах своего DAG и не
шире, а рекламодателей обслуживают несколько DAG'ов на общем `base_dir`: двум из них на
одном расписании достаётся один `scheduled__<logical_date>`.

`advertiser_id` санитизации не требует — `parse_connection` пропускает только
положительное целое. `campaign_id` не требует по той же причине: сегмент приходит из
`_campaign_record` в `hooks/yandex_admetrica.py`, где кампания уже прочитана
положительным целым, поэтому единственный источник этого сегмента доверенный по
построению.

## Key naming rules for `dimensions` / `metrics`

Одна функция `_normalize_name` на оба объекта, четыре шага:

1. Снимается префикс `am:e:` — он называет пространство имён, одно и то же для всех
   имён, которые отправляет провайдер, и повторять его на каждой строке каждого файла
   незачем.
2. Плейсхолдер `<parameter>` заменяется фактическим значением из `extra_params`.
   Параметризованное имя доезжает до API в двух написаниях — значение внутри имени либо
   плейсхолдер в имени и значение отдельным полем, — и оба описывают одну колонку
   одного отчёта; подстановка делает ключ одинаковым для обоих. Плейсхолдер, которому
   никакой параметр не отвечает, остаётся в ключе под именем параметра и читается как
   ошибка везде, куда попадёт: выброшенный, он слил бы все цели аккаунта в одну колонку,
   и слияние было бы заметно только как слишком большие числа.
3. camelCase режется двумя регулярками. `_ACRONYM_SPLIT_RE` заканчивает серию заглавных
   перед словом, которое с заглавной начинается (`RUBRevenue` — валюта и `Revenue`, а не
   одно слово); `_WORD_SPLIT_RE` режет между строчной или цифрой и следующей заглавной
   (`deviceType`, `goal12345Reaches`). Внутри серии цифр не режет ни одна, поэтому
   `interest2d1` остаётся целым.
4. Всё, что не `[a-z0-9_]`, становится подчёркиванием, серии подчёркиваний
   схлопываются, края обрезаются: ключ читается как `dimensions.device_type` и как путь
   JSON, поэтому двоеточию, пробелу или знаку валюты в нём места нет.

Примеры: `am:e:placement` → `placement`, `am:e:deviceType` → `device_type`,
`am:e:operatingSystemRoot` → `operating_system_root`, `am:e:videoCompletePercent` →
`video_complete_percent`, `am:e:interest2d1` → `interest2d1`,
`am:e:goal<goal_id>Reaches` при `extra_params={"goal_id": 12345}` → `goal12345_reaches`.

Поля **внутри** значения группировки этому правилу не подчиняются: они приходят от API
и остаются как есть.

## Token policy

Токен живёт в `conn.password` и читается один раз за жизнь хука вместе со всем
коннекшеном (`_get_connection`). В сеть он уходит одним способом — заголовком
`Authorization: OAuth {token}`, собранным в `_request_page`.

Наружу процесса он не уходит ни одним из каналов:

| Канал | Как закрыт |
|---|---|
| `request_headers` события | Значение `Authorization` не копируется, а собирается заново из схемы и `_mask_token` (`_redact`). Остальные заголовки проходят `_scrub`, чтобы заголовок, случайно повторяющий токен, не стал выходом, которым `Authorization` не является. |
| `request_params` события | `_redact_params`: текстовые значения проходят `_scrub`. Провайдер строит параметры сам, но `extra_params` позволяет DAG добавить свои. |
| `response_body` события | `_bounded_body`: срез сырых байт декодируется, проходит `_scrub` и обрезается. Ответ, написавший токен в кодировке, о которой не объявил, выбрасывается целиком. |
| `error_type` и `error_message` события | `_summarize_error` → `_safe_text` → `_scrub`. Сервер или промежуточный узел вправе отразить заголовок `Authorization` внутри JSON-сообщения, а род отказа — такой же текст сервера, как и оно. |
| Текст исключения провайдера | `_exception_text` → `_safe_text` → `_scrub`. Текст, от которого после этого ничего не осталось, заменяется одним именем типа. |
| `exception_type` / `exception_message` | В событие идёт только тип. Единственный исход, чей текст безопасен по построению, — непарсящийся JSON: `_decoder_position` собирает строку из аллоулиста сообщений стандартного декодера и координат, и из документа не цитирует ничего. |
| Строка в логе таски | Собирается `_attempt_reason` только из разобранных полей: статус, код, род отказа (`error_type`) и сообщение (уже прошедшие `_scrub`), метка непрочитанного тела, позиция обрыва JSON, тип сетевой ошибки. Сырой ответ в этот канал не попадает вовсе. |
| Имя параметра в логе таски | `_resolve_placeholders` пишет имя неотвеченной подстановки — единственный текст вызывающей стороны, который этот модуль выводит целиком, потому что без него WARNING не подсказывает, какой ключ добавить в `extra_params`. Идёт через `_quoted_parameter` → `_scrub`; имя, которое токен пережил, называется длиной. Токен для этого читается в `get_stats` до первого запроса. |
| Текст `test_connection` | Тот же `_exception_text`; искомое значение берётся из уже прочитанного соединения (`_maskable_token`), поэтому отказ не стоит второго обращения к Airflow. |

`_mask_token` показывает 6 первых и 4 последних символа; значение короче
`_TOKEN_MIN_LENGTH` заменяется целиком, поэтому маска никогда не показывает бо́льшую
часть значения.

WARNING-и `parse_connection` называют тип непригодного значения, а не значение.

| `AdmetricaHook._get_token` | `AirflowException` с указанием, куда класть токен и что схему писать не надо |

Не цитировать имя — политика, а не нехватка средств: токен у функции есть, а позиция называет имя, которое надо чинить, не хуже цитаты |
| `AdmetricaHook.test_connection` | не бросает никогда: `(True, …)` с текстом об успехе либо `(False, …)` с текстом отказа, пропущенным через `_exception_text` |
| `sampled`, `contains_sensitive_data` | WARNING: записанные числа — не вся правда о дне, и по строкам этого не видно |
| `data_lag` | INFO: день цел настолько, насколько он есть у API |
| `_named_values`, рассинхрон длин | `AirflowException`: строку другой длины не прочитать, а в `total_rows` она входит наравне с целой |
| Хелперы отчётности в `finally` | два независимых `try`, строка первой: отказ роняет только свою половину с DEBUG, называющей тип (`…the line is dropped`, `…the event is dropped`); исключение в полёте нетронуто |
| `LokiClient.push` | catch-all → один WARNING и выключение клиента до конца жизни; на управляющий поток не влияет никогда |

| `YandexAdmetricaStatsOperator`, пустой список кампаний | файла словаря нет, INFO в лог |
| `YandexAdmetricaStatsOperator`, `date` не в формате `YYYY-MM-DD` | `ValueError` до конструирования хука |

## Decisions and their reasons

### `/v1/stat/data` вместо `/v1/stat/data/bytime`

У `bytime` нет `limit`/`offset`, вместо них `top_keys` с потолком 30 строк, — для
выгрузки с группировками метод непригоден. `/v1/stat/data` с `date1=date2=<день>` даёт
полную выгрузку; дата при этом становится колонкой, которую проставляет провайдер, а
однодневная выборка вдобавок реже попадает под семплирование.

### Запрос на каждую кампанию отдельно

Группировки по кампании в API нет, а `ids=1,2,3` кампании суммирует. Отдельный запрос
на кампанию — единственный способ сохранить разрез вообще. Цена — число запросов,
линейное по числу кампаний, и она принята сознательно.

### `getAllCampaigns` (`/v1/management/campaigns`), а не advertiser-scoped метод

Только он отдаёт `total`, которым закрывается пагинация и сверяется полнота, и поле
`advertiser_name`, попадающее в словарь.

### Кампании не фильтруются ни по статусу, ни по датам

`status` в запрос не передаётся: архивная кампания крутилась в прошлом, и фильтр
`status=active` потерял бы её статистику при перезаливке.

`date_start`/`date_end` в фильтр тоже не идут: справочные даты кампании не гарантируют
отсутствия показов вне их, а пропуск запроса означал бы потерю данных. Лишний запрос
стоит паузы, пропущенный — дня.

### Вложенный JSON вместо плоских колонок

Документация объявляет значение группировки словарём с произвольными строковыми
ключами, где описанием гарантирован только `name`. Набор полей задаётся ответом и не
фиксирован. Вложенная форма переживает и появление нового поля, и его отсутствие в
части строк, не требуя ни выравнивания записей, ни правки схемы таблицы: новое поле —
это изменение значения JSON, а не схемы.

### JSONL как единственный формат

Набор колонок не выводится из запроса и может различаться между строками одного дня.
Табличный формат потребовал бы решить, что делать со строкой, у которой полей больше
или меньше; JSONL этого вопроса не задаёт.

### Ключ строки отчёта — в пределах одной кампании

Отчёт агрегирован по группировкам, поэтому внутри одного ответа комбинация их значений
уникальна. Между кампаниями она повторяется штатно — одна площадка крутится у
нескольких кампаний одного рекламодателя, — поэтому множество ключей обнуляется на
каждой следующей кампании. Общий на всех набор ронял бы выгрузку на совершенно
обычных данных.

При пустом `dimensions` отчёт состоит из одной строки, пагинации нет, и проверка не
применяется.

### Останов пагинации — только по короткой странице

Оба обхода — и статистика, и список кампаний — заканчиваются на странице короче
запрошенной, и ни на чём другом. Объявленный итог служит сверкой результата, а не
критерием останова: заниженный на страницу итог оборвал бы обход на полной странице и
оставил хвост. 10 437 строк при `limit=10000` и округлённом вниз `total_rows=10000`
дают ровно полную первую страницу и совпадение счётчиков; тот же обрыв даёт точный
итог, который следующая страница объявляет большим. Цена — один лишний запрос, когда
данные кончаются ровно на границе страницы.

Флаг `total_rows_rounded` остаётся признаком строгости сверки и запоминается на всю
кампанию (`rounded = rounded or ...`): увидев его один раз, день сверяется мягко,
иначе точное значение на следующей странице вернуло бы строгость, от которой отказ уже
принят. Пока итоги точные, расхождение итогов между страницами роняет день; округлённые
итоги расходятся с WARNING один на обход: приближение вправе отличаться от точного
счёта, но тот же отчёт округляется к тому же числу на любом `offset`, поэтому сменившееся
число — это сменившийся отчёт, и короткий день читается как потеря строк, а не как
округление.

### `accuracy="full"` и `include_undefined=true` по умолчанию

Без `include_undefined` API выкидывает строки с неопределённой первой группировкой, и
сумма не сходится с `totals`. Без `accuracy="full"` цифры плывут между прогонами.
Оба доступны параметрами оператора, поэтому вернуть семплирование можно, а снять их
незаметно — нет: оба имени в `_RESERVED_PARAMS`.

Именно поэтому список зарезервированных имён не сводится к «параметрам, которые ломают
запрос»: подмена `date1` запросила бы другой день, а `_map_row` проштамповал бы строки
датой оператора; подмена `accuracy` или `include_undefined` прошла бы и сверку полноты,
потому что `total_rows` согласован с урезанной выборкой.

### Единственный владелец `snapshot_date`

Поле ставит оператор (`_export_campaigns`), и только он. Той же датой он именует файл и
заполняет `date` в возвращаемой записи, поэтому колонка строки, ключ, из которого она
грузится, и декоратор партиции `campaigns$YYYYMMDD` всегда называют один день. Разойдись
они — строки несли бы день, не совпадающий с партицией, и загрузка была бы отвергнута
целиком. Адрес справочника состоит из одной этой даты: кампании в нём нет ни на одном
уровне, потому что снимок описывает кабинет целиком.

Та же дисциплина держит статистику: `date` в строке, `_date=` в ключе S3 и декоратор
`stats_{advertiser_id}_{campaign_id}$YYYYMMDD` берутся из одной записи, поэтому день и
кампания у колонки, ключа и партиции сходятся по построению.

Хук отдаёт записи API как есть и `snapshot_date` не знает.

### Метка эндпоинта вместо URL в `_request_page`

Адрес берётся из `_ENDPOINT_URLS` по той же метке, что уходит в поле `endpoint`
события. Запрос и описывающее его событие физически не могут назвать разные
эндпоинты, а ключ строк ответа (`_ROWS_KEYS`) находится по той же метке, поэтому один
шаг чтения тела обслуживает оба эндпоинта.

### Гранула хранения — день × кампания

Единица перезаписи равна единице выгрузки: день одной кампании. Оператор раскладывает
строки дня по кампаниям и пишет по файлу на каждую, а дальше кампания входит в каждый
адрес — каталогом в локальном пути и в объекте GCS, hive-партицией `_campaign_id=` в
ключе S3, именем таблицы `stats_{advertiser_id}_{campaign_id}` в BigQuery. Отсюда
свойство, ради которого это сделано: выгрузка части кампаний физически не достаёт до
данных остальных за те же дни, поэтому перезалив выбранных кампаний или сбор одних
только активных ничего чужого не стирает.

В BigQuery второе измерение уходит именно в имя таблицы, потому что гранула нужна
двумерная, а таблица партиционируется по одному полю. Альтернатива — `DELETE` плюс
`INSERT` по `campaign_id` в общей таблице — стоила бы идемпотентности:
`WRITE_TRUNCATE` в декоратор партиции переписывает день одной кампании одной
операцией, а пара DML открывает окно, в котором старых строк уже нет, а новые ещё не
приехали. Цена решения — wildcard-чтение `stats_*` без кэша результатов и без BI
Engine, с требованием совпадения схем; схема из пяти колонок стабильна по построению,
потому что новые группировки и метрики живут внутри JSON-колонок. Вью, попадающая под
`stats_*`, ломает такой запрос целиком, поэтому вью следующего слоя держатся в другом
датасете либо называются не на `stats_`.

Оттуда же и потолок: один запрос ссылается не больше чем на 1000 таблиц после раскрытия
шаблона, а таблица на кампанию делает его достижимым — пять рекламодателей по двести
кампаний уже упираются. Устойчивый адрес чтения поэтому `stats_{advertiser_id}_*`, а
`stats_*` годится там, где кампаний в датасете немного.

`_campaign_id` стоит последним уровнем ключа S3: датой отбирают диапазон, кампанией
сужают внутри него.

Таблицу кампании заводит сама загрузка дня, `BigQueryHook.create_table` с
`exists_ok=True`, и только потом грузит в неё партицию: декоратор `$YYYYMMDD` адресует
партицию существующей таблицы, а состав кампаний известен только после сбора, так что
первый день новой кампании иначе падал бы на несуществующей таблице. Отсюда нижняя
граница `apache-airflow-providers-google>=13.0.0` — метод появляется там, — и она выше
того, что даёт constraint-набор Airflow 2.9.1 (10.17.0), нижней границы поддержки
самого провайдера: инсталляция на этом наборе ставит google-провайдер выше своих
constraints, если ей нужны примеры с BigQuery. Сам провайдер google-провайдера не
требует вовсе, поэтому граница живёт в extra `dev` и в описании примеров, а не в
зависимостях пакета.

Кампания, не давшая за день ни строки, не создаёт ни файла, ни записи, ни каталога, и её
партиция в витрине не перезаписывается: прежние цифры остаются как последние известные
за тот день.

### День едет в витрину циклом внутри таски

Все три примера DAG везут файлы дня питоновским циклом внутри `@task` по
`select_records(records, "stats")`, а не оператором переноса на файл. Число кампаний,
давших строки, известно только после сбора, а динамический маппинг внутри
mapped-группы Airflow не поддерживает — день же и есть map index такой группы.
Декларативным остаётся справочник: он один на прогон, и его адрес известен до запуска.

Следствия у этого три, и они цена гранулы:

- выгрузки и загрузки дня идут последовательно, одна за другой, поэтому день стоит
  столько объектов и столько job'ов загрузки, сколько кампаний дали за него строки;
- день не атомарен в витрине: отказ на кампании N оставляет кампании до неё
  обновлёнными, а остальные — с прежней выгрузкой, и ничто в данных не помечает день
  дописанным наполовину;
- повтор дня (`retries` таски, clear её map index) переделывает день целиком.
  `WRITE_TRUNCATE` и `replace=True` делают это безопасным, но за кампании, доехавшие с
  первой попытки, платят второй раз.

### История не хранится

Перетирается день одной кампании: `run_id` в ключ S3 не входит, а запись статистики
несёт только `date`, `advertiser_id`, `campaign_id`, `dimensions` и `metrics`, поэтому
строку именует день и кампания, а не момент выгрузки. DAG и прогон живут только в
локальном `base_dir` и в промежуточном префиксе GCS, где изолируют параллельные прогоны.

## Development and release

Виртуальное окружение проекта — `.venv`.

```bash
.venv/bin/python -m pip install -e ".[dev]"
.venv/bin/python -m pytest tests/ -v
```

Extra `dev` тянет `pytest` и провайдеров `apache-airflow-providers-amazon` /
`apache-airflow-providers-google>=13.0.0`: в рантайме самого провайдера они не нужны,
но без них не импортируются примеры DAG из `examples/` — `admetrica_to_s3_dag.py`,
`admetrica_to_bigquery_dag.py` и `admetrica_to_bq_and_s3_dag.py`, — которые проверяют
`tests/test_example_s3_dag.py`, `tests/test_example_bigquery_dag.py` и
`tests/test_example_dag.py`.

**Сеть в тестах не используется.** `requests.get` / `requests.post` подменяются через
`unittest.mock`, а `time.sleep` патчится автофикстурой в `tests/conftest.py`, поэтому
лестница ретраев и пауза `request_delay` ничего не стоят по времени. Тест, которому
нужен HTTP, подменяет его на границе `requests`, а не внутри хука.

**Версия** выводится из git-тега через `setuptools-scm` и пишется в
`airflow_provider_yandex_admetrica/_version.py` — файл сгенерированный и лежит в
`.gitignore`, поэтому в чистом клоне без установки `__init__.py` подставляет `0.0.0`.

**Релиз** — это push тега `v*`. `.github/workflows/publish.yml` прогоняет тесты на
матрице Python 3.10 / 3.11 / 3.12, затем собирает `python -m build` и публикует на
PyPI через OIDC (job `publish`, `environment: pypi`, `permissions: id-token: write`).
Оба job-а делают `checkout` с `fetch-depth: 0`: без полной истории `setuptools-scm`
тега не видит и версия получается не той. Заголовок раздела в `CHANGELOG.md` несёт версию,
которую называет тег: версия пакета берётся из тега, а список изменений читают по
заголовку, и разошедшиеся версии означают релиз без описания.
